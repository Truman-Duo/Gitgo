# /publish 需求与验收

## 目标与责任

在 Gitgo 正式终端中完成**协作对齐和本地产出的版本控制**。用户应知道当前事项在做什么、为什么停下、谁负责、下一步可做什么；可以让已确定且获授权的流程自动推进，也可以调整、暂停、接手和恢复。图、表格、对话都服务于这个目标，不是单独的交付结果。

负责人承担领域与交互方案、后端缺口补齐、正式前端实现、联调、失败恢复、迁移与交接。不能仅交前端壳、设计图或演示服务，让项目方自行补后端。HTML 是参考，具体样式和交互自行决定；以下业务效果与验收是要求。

## 一、核心语义

1. Workspace（工作/加工）、Trial（传入/试用）、Formal（正式目标；示例标作 Release）是**角色**，不强制一角色对应一个物理仓。包的 Release/分发记录与 Formal Git 目标分别表达。支持独立三仓验收，也支持个人单仓多角色；目标明确到仓库及 ref，不能推断 origin/master 就是正式目标。
2. 传入贡献可以正式接纳、接到工作/集成分支继续完善、暂不采用；本地产出可以直接整理到正式目标。不是强制 Workspace → Trial → Formal 的串行传送带。
3. 审查意见、内容实际进入哪个目标、剩余工作、分支清理、版本发布分别记录。“代码一般但值得接手”是合法主流程：允许建立加工上下文，保留失败检查、沟通和待办，不将其显示成审查通过、正式合入或问题解决。不得绕过接手操作本身的权限/执行隔离要求。
4. 候选身份绑定固定源 OID/范围/内容、base、目标和依赖。收到修订保留历史，使受影响证据失效并复评。正式接纳验证**最终组合内容**，不能只检查每个候选后直接拼接发布。
5. 相同权限和快照下，共享事实一致。维护者/协作者的默认列表与允许动作可以不同；本地未推送分支、私有草稿等明确标记本地，不自动公开。视图切换不产生权限。

## 二、前端需要设计与实现

| 内容 | 具体要求 |
| --- | --- |
| 事项与进度 | 可定位事项、候选版本、当前节点、等待/失败原因、目标、执行负责人及可执行动作；多事项各有进度，不用一个项目级进度冒充全部状态 |
| 流程理解 | 提供简洁流程图示或等价的可读阶段关系，能分辨计划与已发生、依赖与阻塞；参考“事项列表＋选中项小流程＋进入节点处理”，不把它锁为唯一布局 |
| 节点处理 | 准备材料、检查、接纳选择、正式草稿、交接要求、冲突、执行、发布、清理等进入相应上下文；过去节点看证据、未来节点说明前置条件，浏览不能自动执行/跳过步骤 |
| 终端交互 | 沿用正式组件和焦点语言：单一主要内容区、页头与内容的焦点切换、方向键/Enter/Esc、选中条、底部绿色 CommandBar 和蓝色 NormalBar；不做桌面式无关并列面板。具体菜单、键位及栏位常驻策略由负责人结合现有体系决定 |
| 状态连续性 | 返回恢复所选事项/节点/滚动，保留输入草稿；后台进度不抢输入焦点；空、加载、过期、受限、断线、失败、待核对都有真实状态，不仅用颜色区分 |
| Git 历史 | 按需进入历史/变更/diff，能定位来源与集成结果；提交 parent 图与业务流转图分清。图倾向横向、稳定线道、清晰分叉/合并；具体库和终端实现先验证，不强制 Serie |
| 讨论与审阅 | 查看材料、写意见、交接、待回复和修订上下文；关联正式任务/主进程/子进程，按需跳转并可返回；不要求持续并列图和聊天，不新增互不相通的独立聊天系统 |
| 配置延续 | 提交格式、隐私、远端融入新入口，原数据/用途不能丢。配置可以是场景内入口，不强制保留三个顶层页头 |

前端必须通过正式后端读取与执行，不能从进度动画、页面访问或模型文字推导成功。长列表/图按需加载，中文、emoji、宽窄窗口和终端 resize 要能使用。

## 三、后端需要设计与实现

### 业务与内部 API

- UI 和 Agent 工具共享同一业务操作、状态和授权；支持查询事项/材料/当前步骤/能力、调整计划、执行/暂停/恢复、提交决定或草稿、接收修订、查看结果与关联任务。明确 API 版本、稳定身份、错误与恢复契约，名称和传输由负责人决定。
- 主 Agent 负责语义审阅、是否委派及协作沟通；可以委派子 Agent 处理，不强制另起一个常驻发布进程。Runtime 管任务推进，业务服务做确定性材料准备和操作。用户明确操作可直接通过应用入口，不必先让模型转述。
- 预先确定并获授权的步骤可自动推进；明确策略适用对象、停止边界和修改生效点。配置开关不等于一次正式合入、推送或外发批准，也不重复索取已有效覆盖该动作的授权。
- 请求幂等、版本/预期 tip 校验、任务身份与因果关联、并发冲突、取消边界、重启恢复、外部结果不明后的核对需设计并验证。页面关闭不影响任务事实。只读查询不能顺便触发 triage、测试或模型工作。
- Git、业务记录、平台对象各自事实权威明确；平台没有幂等/条件写支持时不能许诺严格恰好一次。复用已有存储、审批、事件/任务机制，不建立平行授权数据库。

### 保留已有配置含义

| 功能 | 保留和补齐的效果 |
| --- | --- |
| 提交格式 | prefix、编号起点/补零、模板及提交插件影响正式消息；预览与实际提交一致。正式编号不等于产品版本；并发编号协调、模板/插件缺失应明确失败，不假装成功 |
| 隐私 | 路径包含/排除、内容扫描层级、严重度、深度扫描、规则/指纹例外作用于实际出站内容；检查绑定候选与策略版本，策略或内容变更复核。Git push、Issue/评论附件、包分发不能绕过统一规则 |
| 远端 | 保留远端配置及 Trial/Formal 入口的能力；扩展为明确仓库/角色/目标、平台实例和账户关联；地址不夹带凭据，切换目标后刷新能力与证据 |

### 协作、集成、分支、包

1. **Issue/PR/MR 与评论是核心范围**：列表/搜索分页、详情、创建、权限允许的编辑、关闭/重开、关联候选；评论读写和有权编辑、引用回复、草稿、待回复。普通评论、diff 审查线程和不可编辑的操作事实分别建模；旧修订锚点保留。发言账户、目标和可见性明确，AI 草稿不自动变成用户已发送评论。bare Git 无平台讨论时标记本地笔记或未支持。
2. **集成的目标与方法分开**：新建加工分支、进入已有集成分支、进入 Formal；按目标能力提供 fast-forward/merge/squash/rebase/cherry-pick 或部分补丁采用。支持两个贡献的组合和冲突处理，保存来源/作者/结果映射及剩余工作。选择提交必须形成对应内容候选，不能只拼接提交消息。无需一次实现所有方法，但 M0 要列出首批支持组合与后续项；正式默认策略和至少一种工作分支集成路径必须交付。
3. **分支生命周期独立**：用途、责任人、依赖、保留原因、清理条件和恢复窗口；清理前检查新增提交、其他 PR/候选依赖、活动 worktree、未保存修改、所有权和目标版本。合入不自动等于可删；不重写正式历史，不清理别人的分支。
4. **版本与包**：产品版本/tag、固定源码清单、构建或 CI 产物导入、构建日志/环境、产物 digest/大小/平台架构、Release 草稿、发布说明、逐目标上传/下载校验、渠道和保留。Git push、创建 tag、平台 Release、包可下载分别确认；部分失败按目标恢复，未知结果先核对；已有同名 tag 不自动覆盖。可以复用现有构建/registry，不要求新造通用打包器。
5. **多平台**：Git 访问、协作、构建、产物分发按能力组合；扩展现有 GitHub/GitLab 适配，包含自建地址、多账户、分页、限流与权限变化；定义自有平台 adapter 契约。首版跑通 GitHub 完整协作与一种真实分发、自建 GitLab 的关键协作路径、bare Git 降级。更多 registry/平台可分期，不能把模拟 adapter 当跨平台完成。
6. **多人共享**：平台原生对象以平台为权威；Gitgo 独有共享元数据明确存放与同步位置。多台设备各保存 SQLite 不等于协作同步；本地草稿/任务执行状态与共享事实区别开。

## 四、分期与负责人应交付的设计

本 Issue 是整体交付范围；可拆子任务/PR 分阶段验收，不应在首阶段完成后把剩余范围隐去。

| 阶段 | 交付与退出条件 |
| --- | --- |
| M0 设计与验证 | 当前主线差距清单、对象/权威/内部 API/迁移方案、角色与流程关系、终端交互样例和图形可行性、平台能力矩阵、逐阶段工作量/依赖/边界；确定前后端责任与需要项目方选择的问题 |
| M1 核心闭环 | 正式终端事项/流程/节点 + 确定性材料 + Trial 三叉 + 本地正式整理 + 可调自动推进 + 三项配置；真实后端和内部 API 联通，过期/失败/恢复有证据 |
| M2 协作与生命周期 | 真实两账户 Issue/评论/返工、工作分支接手、多候选组合、主/子任务绑定、分支保留与清理；不同角色视图不改变事实或权限 |
| M3 版本分发与跨平台 | 固定源码到实际包/Release/分发，第二平台关键路径、bare Git 降级；故障与迁移验证、正式打包、交接和维护说明 |

M0 先解释设计，不要求以原型为最终方案。工期由负责人核对主线和试做后估算，本 Issue 不预先承诺日期或合同条款。

## 五、验收清单

- [ ] **正式界面**：从 `run_dashboard_native.bat` 启动完整 Bun/Ink Dashboard，在真实可显示颜色的终端走完整流程。主题、焦点、输入、消息、状态栏和 resize 与现有前端一致；HTML/隐藏 PTY 不是此项证据。
- [ ] **真实三仓**：三个隔离 Git 仓中，传入 A 检查失败 → 接手 Workspace → 留下明确返工与沟通 → 修订 → 复评 → 指定 Formal；每步独立用 Git refs/OID/diff 核对，检查失败不会被“接手成功”覆盖。
- [ ] **个人与多角色**：单仓多角色、本地产出直接正式整理均可用；默认分支不叫 master、远端不叫 origin 的样例通过，目标切换不串状态。
- [ ] **流程可控**：自动准备/手动接纳、调整去向、暂停/恢复、候选更新使证据失效；离页与重启不丢草稿/事实、不重复副作用；未来节点不能绕过前置条件。
- [ ] **内部 API 同源**：UI 和真实 Agent 工具访问同一候选与操作结果；实际 task/process/parent 关联可追踪；主进程忙时按原任务接纳/消息规则处理，不伪造 Agent 已执行。
- [ ] **协作沟通**：两个账户/独立 clone，Gitgo 与平台网页往返评论/编辑/修订；旧 review 锚点、权限撤回、网络超时和未知结果可解释，不重复发送。
- [ ] **组合与清理**：接到分支不等于正式合入；两个候选各自通过但组合失败时阻止正式写入；目标 tip 漂移/冲突不覆盖他人内容；有依赖或 worktree 占用时拒绝清理并保留恢复依据。
- [ ] **配置回归**：修改提交格式、隐私、远端影响后续真实行为；旧配置兼容/迁移可验证；缺失插件明确失败；私有内容不得因评论或包分发绕过检查。
- [ ] **包与分发**：固定源码构建或导入真实产物，核对源、版本、digest、tag、平台 Release 与下载结果；模拟中断、部分失败、重复请求后不会覆盖不该覆盖的版本或谎报成功。
- [ ] **多平台与共享**：GitHub、自建 GitLab、bare Git 按约定能力验证；角色仅改变视角和能力，共享事实收敛；权限不可见内容不泄漏名称/数量/摘要。
- [ ] **数据与性能**：图分页绑定快照、只画真实 parent，squash 映射另示；长历史、中文/emoji、快速切项目、断线与过期响应不串数据。M0 登记数据规模、终端尺寸与响应预算，交付时在同条件报告测量结果。
- [ ] **工程交接**：迁移/备份/恢复、API 与能力矩阵、第三方许可和版本、针对性回归与正式打包验证完整；列清已实现/待实施/已知限制，前后端可从干净 checkout 重建。
