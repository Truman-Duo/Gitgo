Create, compose and maintain task-scoped mechanisms as reusable capabilities. The runtime binds actual user provenance, resolves registered versions, compiles typed dependencies, obtains the normal semantic boundary review, and atomically saves the definition plus this task's desired instance. It preserves in-flight work and activates at the next safe boundary. You choose the behavior; Runtime owns source ids, revisions and execution binding.

Use catalog when the needed registered capability or its signature is not yet known. These are building blocks, not a fixed list of task templates. catalog with element_id inspects a component; status with definition_id and optional definition_revision reads that exact saved mechanism, including its callable declaration. Without definition_id, status lists concise current outcomes with a reference to complete saved state. Mechanism definitions live in this registry, not business workspace files; do not search project files or .gitgo for them. A successful call needs no routine follow-up inspection or restatement of bookkeeping; continue the business task. Read a needed json_pointer through tool_result_open only for a real detail, conflict or recovery question.

preview accepts the same declaration as apply, or definition_id plus revision as revise, or definition_id as use. It retains an immutable draft and describes its behavior/difference; it publishes no definition, activates nothing and grants no authority. To proceed with that exact draft, submit the returned next_call: commit with preview_ref only. Do not repeat or rewrite the declaration. Runtime reloads the task-owned draft, rechecks actual sources, contract, definition, instance and component meaning, then performs the normal semantic review and commit fence. A stale/unavailable draft requires a new preview, not a guessed reference. Direct apply/revise/use remains available when no preview is needed.

apply accepts declaration={id,intent,on,calls}. on is a list of lifecycle boundaries. calls is a list of {id,use,parameters,inputs?,when?,after?,version?}. Keep call ids stable during maintenance because runtime state belongs to them. The runtime supplies each call's event input and its go trigger from the subscribed lifecycle event. Other input values must explicitly name a producer output as "call_id.port"; inputs never invent evidence. A when value such as "condition.matches" gates go on that actual boolean; {output:"condition.matches",equals:false} gates the other branch. after names an actual trigger output. Omitting when means unconditional at the subscribed boundary, not a semantic guess. Calls with no data/control relationship do not implicitly run in list order. Exact types, capabilities and cycles are validated by the canonical compiler. Applying an existing declaration revises and stages the same instance; an inactive instance stays inactive.

Example: apply declaration={"id":"task_guidance","intent":"Retain the user's requested comparison criteria","on":["before_context"],"calls":[{"id":"guidance","use":"context.project","parameters":{"content":"Compare observable behavior and preserve the stated constraints."}}]}. This only projects guidance; it neither grants permissions nor proves task completion.

Each call also accepts on=[boundary,...] to narrow its subscription within declaration.on and the component's supported boundaries. Use this when different calls serve different stages: an Agent condition deciding whether to pause a proposed operation belongs on before_tool, comparison belongs on after_tool, and context guidance on before_context. Otherwise an unconditional condition can spend a model request at every subscribed boundary, including ones with no relevant operation. This restriction changes routing, not the semantic criterion. Recent callback evidence distinguishes rejected/unstarted calls, runtime control work and actual business results; reason from those facts rather than counting contract bookkeeping as a business action.

revise accepts definition_id and revision={intent?,on?,calls?,remove?}. calls supplies named additions/edits, merging parameters and inputs into the existing named call; remove lists explicit call ids to delete. Do not use JSON array offsets or rewrite an unrelated call. A changed semantic subset needs an actual predicate capability whose output gates the downstream action. Preserve original obligations, counters and unrelated behavior. A real source or semantic-version conflict requires reinspection; it is not authorization to overwrite another change.

use accepts definition_id and optional definition_revision, instance_id and version_policy (default pinned). It binds the saved definition without manufacturing a new one. When selecting a specific saved version, pass definition_revision on direct use or on its preview; commit retains that preview's exact selection. Omitting it on use or preview selects the latest saved version; pinned freezes the selection, not a version mentioned elsewhere. Check the preview's selected version and meaning before submitting next_call. Reusing a capability does not recursively impose it on every child; declare requirements only when actual intent requires inheritance. Internal publish/instantiate/JSON-graph operations remain compatibility paths for saved continuations, not the normal authoring workflow.

Lifecycle control: suspend(instance_id), detach(instance_id), activate(instance_id,definition_revision?) and reconcile(instance_id). activate without a definition_revision resumes the instance's selected version. require(requirements=[{definition_id,version_policy,definition_revision?},...]) declares which saved mechanisms owned child tasks must inherit; an empty list removes that owner's requirements through the existing boundary. Runtime binds actual task sources, selected immutable definitions and exact instance/owner versions around normal semantic review. Do not look up or copy source_refs or internal counters. Explicit legacy version assertions remain strict, not hints. Reconciliation only reads real recovery evidence and never repeats an unknown external effect. User exit, required-instance ownership, inheritance restrictions and tool permissions remain enforced.

Runtime state and actual tool results are evidence. A successful configuration call is not proof that its callbacks ran. Inspect returned phase: pending_activation retains the old in-flight generation; blocked requires recovery inspection; suspended/detached stays inactive. Never repeat an already committed configuration to repair a notification. Semantic judgments by agent.condition/review remain fallible and do not grant tool permissions. Genuine user control and the original task completion checks still apply. Status guidance never answers a user question. BTW remains read-only until actual user adoption through the existing inbox/contract workflow.

Action inbox: status exposes current candidate ids and bounded text. Choose the actual candidate by meaning, then use inbox_revise(candidate_id,text), inbox_discard(candidate_id), inbox_merge(candidates=[{id},...],text), or inbox_adopt(candidate_id,quote). quote must be the actual user's adoption wording, never a discussion conclusion or your paraphrase. Add instance_id only when the candidate exists in multiple task instances. Runtime binds and rechecks actual user sources, candidate versions and the task contract around normal semantic review; do not copy internal source_refs or revision counters. Revise/merge/discard do not adopt. Adoption creates an original-task change for ordinary scope/plan/verification reconciliation; it does not authorize tools or complete the work. Read a candidate's full retained text only when the bounded status text is insufficient for the chosen operation.

Match each predicate to the stage it controls. Collecting a concrete proposal for later discussion does not require an already adopted task, existing implementation, settled refinement or execution permission. Preserve its unresolved choices as candidate content instead of silently dropping the proposal or inventing answers. Adoption and execution have their own later checks. A proposed additional constraint can be worth retaining even when related work is already a candidate; semantic similarity is not proof that the new requirement is a duplicate. Reject or merge only for the behavior actually requested, not a stricter readiness condition invented by the mechanism author. These distinctions guide Agent judgment; they are not a deterministic rule that every discussion must be collected.
