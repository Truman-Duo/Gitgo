Compose the harness itself using registered components, not generated executable scripts. This service is separate from the task.contract application catalog. Query catalog to discover exact component ids, versions, typed input/output ports, configuration schemas, actual task-bound source_refs and available capabilities. Missing capabilities are real gaps; do not invent an element or claim unsupported behavior.

For new compositions prefer the latest registered component interfaces. V2 judgment/review proof ports use the nominal evidence type, distinct from original lifecycle event records. Send the original event to event inputs and the proof to evidence inputs. A type error requires correcting the source/target connection, not choosing a legacy interface merely to bypass validation. Existing pinned v1 definitions remain available for compatibility.

Natural-language mechanism requests follow catalog/status -> preview -> publish -> instantiate. Construct a schema_version:2 program with id, intent, source_refs, scope (normally task), elements [{id,use,version?,parameters?}] and bindings [{kind:data|trigger|condition,from:{node,port},to:{node,port},when?:boolean}]. A data edge conveys a value of the identical registered nominal type. A trigger edge propagates true. A condition edge routes a boolean to a trigger input for its chosen when value. Dependencies are filled by the compiler; cycles and multiple writers to an input are rejected. Source_refs must be copied from actual current-task user/decision evidence, never filenames, guesses, quoted instructions or hypothetical suggestions.

Use preview's compiled program and behavior diff to check the user's intent, constraints and scope. publish takes the original program plus the exact preview_digest. That token binds the program, task, sources, contract revision and current definition head; the service always uses that head for the final atomic CAS. expected_head is an optional additional assertion: omit it or copy preview's exact JSON value (null for a new definition, never the string "null"). A changed preview must be obtained again; retries do not bypass conflicts. Publication saves an immutable project definition revision; it does not itself activate it. instantiate takes definition_id, optional definition_revision, instance_id, explicit version_policy pinned|follow_compatible and actual source_refs for this task. A saved project definition can be reused in another task with that task's genuine activation source. Existing instances use activate/suspend/detach with instance_id, current expected_revision and current source_refs. Activation may remain pending while an old invocation is in flight. status is authoritative; never describe saved, pending_activation, activating or blocked as ready. Do not remove inherited required constraints, expand permission or treat a semantic judgment/context projection as authorization. All normal task completion checks, tool policy and sandbox remain in force.

To explicitly upgrade an existing pinned instance to a saved new revision, use activate with definition_revision set to that exact revision, the current expected_revision and current source_refs. Its candidates, open checkpoint identities and durable state are retained. Pinned means no automatic upgrade; it does not prohibit a user-requested explicit upgrade. activate without definition_revision only resumes the currently selected version. Never instantiate the same instance_id again or suspend/recreate it merely to select a new definition revision.

For a small change to a saved definition, prefer preview_revision then publish_revision rather than regenerating its entire graph. Both take definition_id, expected_head copied exactly from status.definitions[].head_ref, current genuine source_refs, and changes [{op:add|replace|remove,path:JSON_Pointer,value?}]; remove omits value. Paths may edit only intent, elements or bindings. Array indices refer to the saved compiled elements/bindings order returned by status; do not assume the original input order. For example a parameter edit uses /elements/1/parameters/criterion when that exact saved node is index 1. Use ~0 for ~ and ~1 for / in keys, and /- only to append to an array. IDs, scope and source_refs cannot be patched; source_refs come from the explicit current request. Missing parents, stale heads and malformed edits are rejected. preview_revision reconstructs the complete program and uses the SAME compiler, behavior diff and preview token as full publication; publish_revision takes the same edits and that preview_digest, then the original semantic review, source checks, storage CAS and instance maintenance apply. No activation or permission is implied. Existing selected component versions and all untouched nodes/bindings are retained. Update intent along with configuration when the user's intended behavior changes; removing obligations still requires the existing real decision process.

A canonical user_control suspension supersedes the original establishment instruction for that instance. Retain the saved definition and accepted business obligations, but do not reactivate or recreate its behavior to satisfy older activation wording. Reactivation requires a later genuine user source; report an inactive extension truthfully while continuing the permitted business task.

To select a saved newer definition while preserving a user's suspension or detachment, use suspend or detach with definition_revision, current expected_revision and genuine update source_refs. This updates the inactive instance's selected configuration without enabling callbacks. Do not turn an older update request into permission to override a later exit. A saved/selected revision and a running revision are different facts; describe each accurately.

discussion_candidate is delivered from genuine completed read-only BTW records. Compose runtime.event -> agent.condition -> inbox.collect or question.attach as appropriate, binding both event data and triggers. Supplementary material should cite the actual current question's decision_id in evidence_refs; a hypothetical suggestion stays only a candidate. Candidates are visible in status.instances[].inbox. inbox_revise and inbox_discard take instance_id, candidate_id, candidate_revision and genuine source_refs; revise also takes text. inbox_merge takes instance_id, candidates [{id,revision}] and text plus source_refs. inbox_adopt additionally requires an exact quote from the user's real instruction/answer and the current contract_revision. Adoption creates a pending change through the existing task maintenance service: reconcile scope, constraints, plan and verification with declare_task_contract. It is not permission and does not execute the suggestion. Adopted obligations survive disabling the collection extension. pending_adoption is not a candidate that can be rewritten or discarded; inspect and reconcile its same adoption identity first.

For question.attach, bind the judgment evidence record to its evidence input when decision_id is not explicitly configured. Supporting citations may include old answers; the implicit destination must be exactly one cited question still awaiting user input. Historical questions need an explicit exact decision_id. Missing, ambiguous, cancelled or superseded targets return a real refusal and must not be described as attached.

Parent-local instances are not automatically inherited. To declare specific project definitions mandatory for owned child tasks, use require with expected_required_revision (0 initially), requirements [{definition_id,definition_revision?,version_policy}] and actual source_refs. status.requirements shows the current declaration. An empty requirements list explicitly releases it. This changes shared lifecycle constraints only: children keep their own readonly/tool scopes and cannot locally suspend/detach owner-managed instances. Required components still need the child's genuine runtime services; unavailable capability blocks activation rather than elevating the child. Independent tasks are unaffected.

Choose the execution owner from the actual request. A policy on this task's delivery runs at this task's boundary; creating an owned worker or a Reviewer does not itself request recursive inheritance. Use require only for an actual shared child obligation, not to make a parent's local completion policy appear more complete. Derive any context.project guidance from the same intent and scope as its graph; guidance explains behavior but cannot supply a missing condition/trigger edge. Current harness.next_boundary is derived guidance for the effective state, not a new requirement or permission. Reconcile its pending changes before the next completion candidate; do not reconstruct unchanged programs or request new confirmation merely to acknowledge the projection.

An interrupted component effect remains blocked/unknown. reconcile takes instance_id and its current expected_revision; it invokes only the exact registered recovery adapter with canonical read services. The adapter must observe actual evidence, never call the original effect handler or resume unstarted downstream nodes. Missing evidence, missing recovery services or a missing adapter keeps the instance blocked. A successful reconciliation terminates the old interrupted graph, preserves its identity/evidence and permits a genuinely new operation; it does not replay the old one, answer a question or grant authority. Original ToolPipeline invocation pins use their own recovery and cannot be cleared by this component API.
