Manage versioned requirement/evidence graphs through the existing runtime and question broker. Permissions and mandatory completion checks remain in force.

configure uses a top-level plan object, schema_version=1 (optional). Select profiles from alignment, domain_modeling, diagnosis, tdd, architecture, retrospective, agent_documentation. A custom plan has unique node ids and kinds: decision(state_topic,request), observation(tools), check(test_id,passed), change(files), document(path), report(format). Use kind, not type. depends_on defines the ready frontier; when maps ancestor decision IDs to accepted labels. before_mutation belongs on prerequisites, never change. When extending, retain the complete existing graph and profiles.

Omit nodes only to compile a preset. Presets use test_id/target_files, questions(id,state_topic,request,depends_on), glossary_path, agent_document_path. check_argv/check_cwd bind exact non-pytest checks. preparation_files allows building evidence harnesses before red, not product fixes. Do not probe schemas by installing unrelated presets: they create real obligations.

check.passed is the expected result, never recorded evidence. A ready node is eligible, not complete. Matching actual execution receipts, user sources and document hashes establish evidence. Status alone proves neither interception nor test execution/success. Distinguish schema rejection, readiness, actual blocking, execution and success.

ask(node_id,request) and ask_frontier publish ONE ready question through the broker. request contains question, why_user_must_decide, kind, options. Reassess each actual reply before selecting another frontier. Ask only material user-owned unknowns; inspect factual unknowns with observation tools. Do not interview greetings, invent risks or treat a proposed question as already published. Extend the graph as real answers expose dependencies. revise_decision reopens a confirmed choice and invalidates dependents.

resolve_answer records a source-bound interpretation. Example:
{"operation":"resolve_answer","node_id":"target_node","decision_id":"actual_reply_id","content":{"disposition":"confirmed","value":"meaning supported by that reply","quote":"exact reply substring"}}
content can instead contain the full canonical record including node_id and decision_id. Duplicated identities must agree. disposition is confirmed/partial/deferred/delegated; unresolved input needs remaining. Only confirmed or explicitly delegated answers close gates; receiving text alone does not. source_node_id identifies the actual round question when different from the target. Evaluate whether a later real reply answers an unresolved older/unasked facet instead of asking it again. Never invent a receipt, infer permission, or replace confirmed values without explicit revision.

record(node_id,content) saves a document hash or structured report. retrospective derives findings from actual task receipts. propose_amendment(plan,reason) offers a concrete scope change: weakening requires its matching real user choice. Unavailable checks never become passes. A read-only exploratory response can preserve the original unresolved choice.

Example configure call:
{"operation":"configure","plan":{"profiles":["retrospective"],"nodes":[{"id":"inspect","kind":"observation","tools":["status"]},{"id":"retro","kind":"report","format":"retrospective","depends_on":["inspect"]}]}}
The graph belongs in plan, not content. Field/schema errors need corrected arguments, not new user intent, another interview or weaker requirements.
