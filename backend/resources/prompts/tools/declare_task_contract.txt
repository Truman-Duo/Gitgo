Compile your semantic understanding of a non-trivial user request into a Host-validated task contract before effectful or delegated work. This is not keyword classification and grants no authority. Do not call it for ordinary conversation. Record whether delegation or concrete workspace artifacts are genuine requirements; list any unresolved product choice so request_user_decision can handle it. For bounded single-owner work, choose self_execute. Continue directly when the delivery is only a response or uses observation-only tools; request_self_execute only before an actual mutating delivery. Delegation is valid only for truthful complexity, multiple workstreams, explicit handoff/parallelization, or a user's manual B request. When the user explicitly asks for a subprocess/B, set user_requested_delegation=true and quote the relevant request in user_request_evidence; do not infer this flag merely because delegation would be convenient. If the wording is ambiguous, put that ambiguity in uncertainties and ask the user instead of guessing. The result includes a deterministic Budget Card. Treat a B as having setup and coordination cost: persisting or testing an answer A already derived is still bounded single-owner work, not a separate workstream. When this task needs results from previously delegated work, select adopt_process_ids from list_agents to make those child outcomes required for this turn. Unrelated new tasks must not inherit old delivery obligations automatically.

Initial declare requires only goal, execution_mode, deliverables and acceptance_criteria. Runtime supplies version/source bindings, default required=true for deliverables, and the absent negative delegation flags. Omitted initial uncertainties means no additional concern proposed, not proof that everything is known; actual open questions and independent requirement checks still apply. List real unresolved business choices explicitly. A nonempty initial uncertainties list keeps requires_user_decision=true unless you explicitly judge otherwise. Tool selection, completion protocol and Runtime setup are not user-owned product choices. On revise, omitted uncertainties and decisions are preserved, never cleared by these initial defaults.

Use one concise business plan (plan) with meaningful work and verification. engineering_workflow is optional extra evidence policy; do not translate every plan step into a second DAG. For a suitable registered practice, supply its concrete test/path inputs and let Runtime generate node ids and dependencies. A change node means an actual file mutation and requires files; mechanism configuration belongs in the business plan, not a fake file-change node. A check requires an actual registered test_id and passed boolean; never invent a test identity. Configure custom nodes only when their evidence relationships are genuinely needed.

General examples (replace goals, paths, tests and choices with actual task facts; these examples grant no authority):

Initial bounded work:

```json
{"goal":"Preserve the parser API while correcting empty input handling","execution_mode":"self_execute","deliverables":[{"kind":"workspace_file","path":"src/parser.py"}],"acceptance_criteria":["Empty input returns the documented value; existing parser tests pass"],"plan":{"summary":"Inspect, correct and verify the parser","steps":[{"id":"inspect","goal":"Inspect the parser and existing tests","verification":"Identify the current behavior and concrete verification"},{"id":"fix","goal":"Correct empty input handling without changing the public API","verification":"Run the existing parser tests and inspect the diff"}]}}
```

An actual unresolved product choice:
```json
{"goal":"Add configurable output formatting","execution_mode":"self_execute","deliverables":[{"kind":"workspace_file","path":"src/format.py"}],"acceptance_criteria":["Implement the user's chosen default without changing existing explicit formats"],"uncertainties":["Which default output format does the user want?"],"requires_user_decision":true}
```

Optional TDD evidence policy, only after discovering the real registered test. Runtime derives target_files from the declared workspace_file deliverable and builds the fail/change/pass graph:
```json
{"goal":"Correct the parser regression using its registered test","execution_mode":"self_execute","deliverables":[{"kind":"workspace_file","path":"src/parser.py"}],"acceptance_criteria":["The existing failing parser test passes after the correction"],"engineering_workflow":{"profiles":["tdd"],"test_id":"parser_regression"}}
```

Incremental revision, retaining all earlier obligations and unresolved choices:
```json
{"operation":"revise","append":{"acceptance_criteria":["Also verify the newly requested unicode case"]}}
```

For an already declared task, use operation=revise and supply only changed semantic fields; Runtime preserves omitted fields and binds the current revision. Use append to add acceptance_criteria, deliverables, uncertainties, required_tool_calls or adopt_process_ids without copying their existing arrays. Supplying an array directly replaces that field; do not replace and append the same field together. For example, operation=revise with append.acceptance_criteria adds actual verification requirements. Resolving uncertainty still requires your explicit semantic choice; Runtime never assumes a user answer clears obligations. Merely appending discussion text is not a scope revision. expected_revision is optional for revise and is enforced if supplied. Legacy full replacements still require expected_revision. A revision conflict requires reconciling the returned current contract before retrying, not blindly replaying old changes. Omitted engineering_workflow preserves the active plan. Removing or replacing its obligations requires the existing explicit scope-amendment decision. The activation receipt identifies the exact revision and persistence boundary; it never grants sandbox or tool permissions.

Ownership is separate from scope revision: when the supervisor continues its own work, use routing_transition=keep_supervisor and omit adopt_process_ids. continue_owner means continuing an existing owned worker, not the current process; select only actual child identities from list_agents. Adopt child outcomes only when they must become required for this task. A scope revision or an existing independent Reviewer does not by itself require adopting a child or creating another one.

Supply plan and related_review directly when declaring or revising the task; Runtime binds the maintenance revision and validates both with the same atomic contract update. Keep the plan proportional: concise business steps and their verification, without restating Runtime callbacks. If adopting pending feedback, include maintenance.resolve_changes together with the revised plan and affected acceptance requirements in that one call; a separate acknowledgement cannot reconcile scope. An explicit maintenance.expected_revision remains an exact concurrency constraint. Callable lifecycle mechanisms are authored once with harness_mechanism, not copied into this contract's legacy task-state graph. Declaring business requirements does not require re-declaring an already installed mechanism.

For an actual maintenance trigger already covered by the current plan (for example an expected baseline test failure), use operation=revise, plan_review={action:"retain",reason:"why the existing steps and verification still cover it"}, and maintenance.resolve_maintenance=[actual trigger ids]. Runtime retains the exact plan and dependencies; do not recopy its steps. This is your explicit semantic judgment, not an automatic dismissal of failures. Changed business scope or adoption still needs a revised plan and affected acceptance requirements. Unavailable retained dependencies and concurrent changes remain blocked.

Delegation creation and waiting for a delegated result are separate requirements. If the user explicitly requests an auxiliary independent child but says the parent must not wait for its result, retain user_requested_delegation=true and quote that instruction, explicitly set minimum_delegated_outcomes=0, and create that child with required_for_parent_completion=false. The Host still checks that the requested child actually exists. Omission retains the legacy minimum of one required result; zero does not release another child already declared required. Do not manufacture a completion dependency merely because an independently scoped child is awaiting its own user input.
