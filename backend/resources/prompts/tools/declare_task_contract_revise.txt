## Revise an accepted contract
- When new evidence reveals a missed consumer, old promise or missing check, verify the smallest relevant path and update the affected obligations. Keep unevidenced possibilities as concerns and preserve unrelated decisions.
- Send operation=revise with only changed fields. Runtime preserves omitted values and binds the current base revision. Append to extend acceptance_criteria, deliverables, uncertainties, required_tool_calls or adopt_process_ids. An array supplied directly replaces the field. Choose one method per field. Example: {"operation":"revise","append":{"acceptance_criteria":["Verify Unicode input"]}}.
- A supplied expected_revision is exact. Legacy complete replacement requires it. Reconcile conflicts against the current contract before retrying. Resolve uncertainty semantically. Removing or replacing active workflow obligations requires the existing scope amendment.
- For an adopted change, provide affected requirements, plan and related_review together with maintenance.resolve_changes [{id,reason}]. Runtime binds one change to the submitted delta. For multiple changes give the fields for each. Optional work_item_ids identify steps needing fresh evidence. Keep unaffected step IDs. If a real maintenance trigger is already covered, resolve it with maintenance.resolve_maintenance and plan_review={action:"retain",reason:"why the current plan still covers it"}. This keeps the original plan and its dependencies.
- When the supervisor stays responsible for its existing direct work, use keep_supervisor. continue_owner selects an actual owned child from list_agents. Main-process verification after delegation can use request_self_execute for the needed tests under the accepted contract.
- When changing the scope of an existing worker assignment, select the affected assignment_scope in the current user change. Use handoff_to_worker when transferring observed work to a worker.
