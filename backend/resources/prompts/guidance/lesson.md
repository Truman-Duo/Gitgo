# Lesson

## Identify the feedback kind

Separate advisory recall, registered checker rejection and post-commit observation warnings.

## Revise a rejected candidate

For a rejected candidate, inspect lesson_feedback, its applicable conditions, registered check, lesson version and candidate binding. Revise and resubmit against the current file version through the same governed path.

## Review applicability without bypassing checks

A checker unavailable result is not a pass; restore the required check or use the existing explicit decision path if the mechanism offers it. Do not disable the check, rewrite the lesson to silence it, or switch executor to evade it. A questionable lesson can be discussed/revised through the existing lesson review path without making an unconfirmed candidate authoritative.

## Preserve successful effects

Recall/excerpt warnings do not undo a successful write: recover retained evidence or the observer without repeating the write. An empty recall is not proof that no relevant experience exists.

## Observation example

- Appropriate: a file commit succeeded but excerpt capture failed; recover the observation and retain the successful write.
- Inappropriate: repeat the write to make the observer succeed.

A text-pattern match can include comments or strings. It proves the configured pattern matched, not that a forbidden call executed. Inspect the lesson's applicability and checker contract when this distinction matters; use the existing review path for a questionable lesson without bypassing the active check.

## Before-write advice and request state

LESSON_FEEDBACK_REQUIRED leaves the target unchanged. Consider the actual returned advice, then revise the candidate or reference its lesson_feedback_id to keep the same candidate. The identifier is not a user approval or a checker pass. A changed file baseline, candidate or lesson version needs fresh feedback. Do not manufacture a query, acknowledge an unseen result or switch executors to avoid the feedback. A completed lookup with no matches, a failed lookup and a partially shown result are distinct states.

Ordinary advice may be unavailable while mandatory checks still succeeded; the write may then complete with a warning. Do not retry that committed write or describe the unavailable advice as checked. If mandatory inventory or checks are unknown/unavailable, the target stays unchanged and the original recovery or exact authorization path applies.

A user may request a project check in conversation or BTW. Use the mounted lesson_checker schema to inspect the exact lesson version and propose its supported declaration through one real permission card. Saving knowledge, a requirement answer or a side discussion conclusion does not enable enforcement.
