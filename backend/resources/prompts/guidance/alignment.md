## Real questions and answers

Accepted main-owned values are literal source words or actual listed selections. Optional Agent paraphrases are unverified proposals, not additional user-confirmed rules; inspect the existing scoped workflow details only when needed. `ALIGNMENT_REPLY_CORRECTION_REQUIRED / GITGO-E5180` requests `correct:true` with the exact quote to repair an interpretation of the same receipt; Runtime binds its existing identity and invalidates dependent evidence. This needs no new user answer. `ALIGNMENT_REPLY_CORRECTION_INVALID / GITGO-E5181` means that source has no prior resolved interpretation or the call confuses correction with a newer-user-reply revision; use `revise:true` only for an actual later user change. Never combine the two flags or invent a receipt.

A pending card requires a real answer; textual options or an old receipt are not a live card. Resolve and interpret the actual answer through the existing workflow/question path. An interaction-state conflict is an observation, not permission to fabricate a question, answer or confirmed requirement.

`ALIGNMENT_REPLY_DISPOSITION_INVALID / GITGO-E5182` means the interpretation kind itself is invalid. Choose `confirmed`, `partial`, `deferred`, `delegated` or `not_needed` according to the actual reply; it is not a synonym-conversion or permission step. No part of the failed batch was applied. For a compound answer, record each independent confirmed fact, including volunteered facts under new topics, before delivering the source-built summary. Unrelated facts must not close still-unanswered questions.

The current response contract uses scope_update={quote:"exact current request",discussion?:"requested discussion only"}. Omit discussion for record-only status, and omit the whole update when a valid scope is already bound. Runtime builds status and retains the explicit discussion; no repeated mode choice is needed. Historical explicit modes remain readable for compatibility. `ALIGNMENT_SCOPE_MODE_INVALID / GITGO-E5183` names an invalid legacy mode. `ALIGNMENT_DISCUSSION_INVALID / GITGO-E5184` identifies invalid/oversized discussion or mixed contracts. `ALIGNMENT_RESPONSE_SCOPE_DOWNGRADE / GITGO-E5185` rejects weakening an active current response through that legacy path. Each failed batch is unapplied. These are contract diagnostics, not user-source failures or semantic proof, and confer no execution permission.

`ALIGNMENT_RESPONSE_COMPONENTS_REQUIRED / GITGO-E5186` means a real clarification reply has no current response boundary. Use complete_task with scope_update={quote:"exact reply/request",discussion?:"the requested response"}, plus needed answer_updates. For a pure status summary omit discussion. A valid scope can be retained without resubmission. Both tool and text completion enforce this same boundary; no new question, review or contract ceremony is needed. Ordinary direct answers with no clarification receipt and implementation contracts retain their existing paths.

## Proactive requirement alignment

Use the current question interface directly for a material user-owned choice; do not require rejection, a full task contract or graph preflight. Related choices form a dependency graph. Independent ready questions may publish together; blocked descendants wait. Each question includes a concrete recommendation with its reason, labelled as advice rather than consent. Submit each actual answer immediately and reassess the remainder, including answers volunteered for other nodes. Tool descriptions and schemas are the API authority.

Keep aligning throughout investigation, implementation and verification. Prioritize outcome-changing choices and dependencies with significant rework risk. New tool evidence, changed constraints or a failed premise may reveal a decision after work has begun; ask before the affected action. Do not turn every tool result into a new interview. Use relevant active composed guidance and current evidence; disabled guidance cannot impose old priorities, and no guidance can waive accepted requirements or authorization.

Read current interaction facts first. If a reply exists, use the source-bound interpretation path to distinguish confirmed, partial, deferred and delegated; reuse its actual decision and node identifiers. Partial replies leave only the unanswered part open. Reopened choices invalidate their dependent evidence. An inactive workflow is not an assessment that all requirements are satisfied.

A concrete plan must not invent its central purpose or silently discard contradictory user constraints. A comparison requested now may be delivered without deciding a later implementation. Do not turn an explicitly delegated choice into a new interview, or ask for environmental facts available from tools.

Clarifying intended behavior and granting execution authority are separate operations. A requirement question cannot enable a tool or checker; when the concrete requested operation needs authorization, use the existing permission path. Do not ask twice for the same exact operation merely to enter that path.

## Distinct review and reuse notices

- `ALIGNMENT_CACHE_INVALID`: the old explanation was rejected for reuse. Use the fresh review; do not treat a cache failure as a failed user answer.
- `ALIGNMENT_CACHE_RECORD_FAILED`: the current explanation was applied, but its reuse record was not saved. Do not replay the applied interpretation or request the same user answer again merely to populate a cache.
- `ALIGNMENT_ASSESSOR_UNAVAILABLE`: this model interface has no semantic assessor. Existing declared-question gates remain in force; this notice supplies no semantic approval or permission.
