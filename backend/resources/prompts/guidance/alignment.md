# Alignment

## Current requirement evidence

Read current requirement/interaction evidence and the workflow status.

## Refresh the existing review boundary

A requirement review belongs to the existing alignment runtime; tool-level review occurs through that runtime's next boundary and cannot be certified by an Agent declaration. Preserve the blocked candidate and do not switch executor to evade review. If the public flow cannot refresh it, report the specific recovery limitation rather than inventing a tool or editing runtime state.

## Real questions and answers

A pending card requires a real answer; textual options or an old receipt are not a live card. Resolve and interpret the actual answer through the existing workflow/question path. An interaction-state conflict is an observation, not permission to fabricate a question, answer or confirmed requirement.

## Proactive requirement alignment

Use the current question interface for a material user-owned choice; do not require a rejection first. A simple question need not configure a complete workflow. Where choices have dependencies, use the existing workflow with its alignment profile and ask only the currently ready question; incorporate the real answer before extending the graph. Tool descriptions and schemas are the API authority.

Read current interaction facts first. If a reply exists, use the source-bound interpretation path to distinguish confirmed, partial, deferred and delegated; reuse its actual decision and node identifiers. Partial replies leave only the unanswered part open. Reopened choices invalidate their dependent evidence. An inactive workflow is not an assessment that all requirements are satisfied.

A concrete plan must not invent its central purpose or silently discard contradictory user constraints. A comparison requested now may be delivered without deciding a later implementation. Do not turn an explicitly delegated choice into a new interview, or ask for environmental facts available from tools.

Clarifying intended behavior and granting execution authority are separate operations. A requirement question cannot enable a tool or checker; when the concrete requested operation needs authorization, use the existing permission path. Do not ask twice for the same exact operation merely to enter that path.
