# 治理可用性调查（2026-10-08）

结论：用户观察有实际依据。Gitgo 已有不少机制治理，但把机制的说明、行文规则和当前状态重复放进模型上下文，形成了“前台治理”的压力。问题不应靠再加一句“不要表演治理”解决。应收敛模型必须理解的协议，把约束执行、事实验证和进度投影继续放在 Host。

本次只调查治理，不改变治理策略。终端连续性是另一个已实现的改动。

## 实际 trace

读取一个隔离终端测试项目的数据目录，通过只读 SQLite 查询和 CAS provider 快照核对；未依赖模型自述推断实现。可重复工具为 `scripts/audit_prompt_surface.py`，支持还原 `prefix_delta`，不打印对话内容，不打开 StorageRuntime，不改变数据库。公开报告省略实际项目身份。

| 内容 | 实测 |
| --- | ---: |
| 稳定系统说明（行为、协作） | 2,660 字符 |
| 系统任务契约（身份、权限、工具、环境、交互） | 5,411 字符 |
| 每次请求尾部的 CURRENT-TURN ENVELOPE | 3,155 字符 |
| 每次附带工具数量 | 34 |
| 工具 schema 紧凑 JSON | 19,669 字符 |
| 首轮用户输入“你好” | 2 字符 |
| 用户明确说正在调试的输入 | 20 字符 |

系统说明与当轮信封合计 11,226 字符；这些量在该对话的七次 provider 请求中保持相同。最后一份完整快照为 110,561 字节，包含历史和 provider 状态，并不等同于实际 HTTP 请求长度。这些统计是字符/字节，不能换算为精确 token 或实际收费。缓存可以改善成本，但不会消除指令对行为的影响。

本次样本没有累积的 HOST TASK CONTRACT UPDATE；因此不能把当前问题归咎于契约更新堆积。已有另一份历史会话出现过此类更新，长期上下文仍需单独评估。

## 两个抱怨分别意味着什么

**信封过长：成立。** `prompt_compiler.py` 的能力清单与 provider 工具 schema 重复；`executor.py` 又在每次请求末尾列出所有可用工具、权限阶段与契约入口。即使只是问候，也收到完整的八类提问分类、工作流说明和交付约束。问题既是总量，也是治理词汇占据默认交互的比重。

**调试时不能报告过程：不是绝对禁令。** `prompt_compiler.py` 的行为标准、answer 交互契约，以及 `executor.py` 当轮信封，都保留了用户要求审计时的例外。`complete_task` 的交付说明也有类似边界。模型说它被绝对禁止，不能据此认定代码确实绝对禁止。

但这些地方反复强调省略过程，调试意图却没有成为持久、结构化的交付目的。模型必须临场识别“我正在调试你”属于例外；这个例外在下一轮也缺少明确继承。重复的默认禁令与隐含的例外容易发生竞争。这个判断是代码与样本支持的解释，尚不是 A/B 实验确立的因果结论。

模型关于“感觉”“犹豫”的说法不能作为机制可靠性的证据。调试应该呈现可观测的请求、工具返回、阻塞原因、恢复路径和用户决策，而不是索取内部思维过程。

## 已有基础设施可以复用

| 已有机制 | 应继续由机制承担的事情 |
| --- | --- |
| capability profile、动态工具注册表、执行 lease | 工具可见性与写入权限，不靠模型自律 |
| ToolPipeline、权限 broker、sandbox、执行回执 | 参数校验、敏感审批、效果验证、组合工具逐叶检查 |
| completion evidence / Host completion evaluator | 真实完成条件、测试证据、禁止自批 |
| engineering_workflow 的类型化依赖图 | 对齐、诊断、领域建模、TDD、架构等实践的必要前置条件 |
| decision ledger、事件与 UI 投影、CAS | 记录过程、展示状态、按需读取证据 |
| semantic task contract | 接收模型对意图的结构化解释，再由 Host 校验与编译 |

因此不能说当前治理“只有提示词”。但机制存在，也不代表所有行为已经靠机制自然导出，更不证明比传统 harness 稳定。尤其是哪些实践适用、何时需要提问、怎样向用户交付，仍有不少语义判断落在模型及冗长说明上。

## 建议的实施顺序

1. **先建立测量基线。** 用真实 trace 建立普通问答、调试审计、工程执行、受限失败恢复的回放集。测量多余工具调用、无必要提问、交付遗漏、指令体积、失败恢复及真实权限拦截。稳定性需加入长任务、上下文压缩、Provider 故障和依赖失败场景。
2. **把交付目的做成契约的一部分。** 普通回答、变更交付、审查、调试审计各有明确的证据需求和展示边界。复用现有 task contract / decision ledger；由模型解释语义，Host 校验，用户可显式调整。不要用 Host 的关键词规则猜“debug”，也不要把它混同于 plan/self_execute/delegate 这些执行路线。
3. **统一模型可见的当前状态。** 复用有效工具注册表和权限状态，编译简短的当前能力/下一项必要动作。常态只提供必要的语义说明；阶段变化、阻塞、恢复时发送明确增量。完整事实和证据通过已有工具/CAS 按需读取。应消除三处工具清单和多处同义禁令，而不是添加一个新提示词层。
4. **保留硬约束，降低仪式要求。** 审批、效果回执、必要验证、依赖顺序继续强制执行。工程实践按任务契约和风险适用：不要求每项低影响工作填写完整流程，也不把“提交表单”视作完成工作的证据。无法满足前置条件时，返回可理解的原因、恢复选项及通知，不能静默跳过，也不能盲目循环补表。
5. **从事件生成可观测过程。** 普通交付只展示对用户有用的结果、限制与等待决策；审计交付可直接读取结构化执行事实。后台进度与治理状态由 Runtime/Host 事件投影到 UI，减少让模型“汇报自己正在治理”的需求。

这些改动不是追求零提示词。意图解释、工具语义与协作边界仍需要语言说明。目标是只有需要推理的部分交给模型，可机械执行的部分交给机制；治理强度与提示词长度、状态报告数量分开评价。

验收必须同时证明两件事：日常互动更直接，真正越权或证据不足时依然被拦截。单纯缩短回答或降低工具数量，不能证明治理更好。
