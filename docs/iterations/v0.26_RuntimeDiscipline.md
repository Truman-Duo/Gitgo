# Gitgo v0.26 — Runtime Discipline

> 2026-05-29 | 基于 v0.25 State Convergence | 不扩功能，定义约束

---

## 定位

v0.25 定义了"有什么"——三层状态、9 种 governance event、StateReader 统一查询。
v0.26 定义"什么不能做"——不是新功能，是**硬约束的显式声明**。

v0.20-v0.24 是功能生长。v0.25 是状态收敛。v0.26 是**收敛的固化**——如果这层约束不做，
下一个版本很容易滑回：加一个新 subsystem，自己维护自己的状态，自己决定自己的 event，
三层边界形同虚设。

## D1: Runtime Discipline 文档

`docs/RuntimeDiscipline.md` 包含四个部分的硬约束。不声明"将来应该"——只声明**v0.25 代码已经成立的 rules**，违反即 bug。

### 1. Canonical Events

9 种 governance event 是闭集。新增 governance event 需要修改这份文档。

```
governance_synced         (sync_session.py:816)   step_sync() 成功后
governance_pushed         (sync_session.py:945)   step_push() 成功后
governance_dissolved      (sync_session.py:730)   step_dissolve_formal() 成功后
governance_edited         (sync_session.py:673)   step_edit_formal_message() 成功后
governance_renumbered     (sync_session.py:702)   step_edit_formal_number() 成功后
governance_drift          (commands.py:454)       push 前 drift 检测时
governance_contract_updated (sync_session.py:845) contract 自动更新后
governance_lesson         (sync_session.py:856)   lesson harvest 后
governance_memory_snapshot (sync_session.py:829)  memory snapshot 后
```

操作级 event（`scan` / `formalize` / `sync` / `push` / `triage_*` / `delete_formal` / `dissolve_formal`）是 workflow log——它们是独立的 `operation` 名前缀，不与 governance event 混用。两者区分标准：governance event 的 detail **包含状态变更的具体内容**（如 `{"commit": "[MYAPP-1]"}` 或 `{"commits": [...]}`），操作级 event 的 detail **包含操作的范围**（如 `{"entries_total": 45}` 或 `{"file_count": 12}`）。

### 2. State Authority

每个持久化 state 有单一写入源。基于 RuntimeStateModel.md 的状态清单。

| State 字段 | Authority | 禁止直接写入者 |
|-----------|----------|---------------|
| `formal_commits[].synced` | step_sync() | 任何其他方法 |
| `formal_commits[].pushed` | step_push() | 任何其他方法 |
| `formal_commits[].message` | step_edit_formal_message() | 直接赋值 |
| `formal_commits[].number` | step_edit_formal_number() | 直接赋值 |
| `contract.tech_stack` | ContractManager | 直接读写 contract.yaml |
| `contract.decided_features` | ContractManager | 直接读写 contract.yaml |
| `*.jsonl` (lesson) | LessonManager | 直接读写文件 |
| `.gitgo/memories/` | snapshot_tool_memories() | 直接读写文件 |
| `gitgo_history.json` | HistoryManager.add_operation/add_suggestion | 直接读写文件 |

违反 authority 的代码是 bug——即使在当前测试下不崩溃，它造成了"同一个 state 被两个不协调的写入者修改"的语义风险。

### 3. Derivation Rules

Semantic 层的所有字段从 operational + governance 层计算。当前已成立的规则：

- `workspace_entropy` = f(entries_changed) → 不持久化
- `suggested_next_action` = f(trial_pending, entries_changed, formal_synced, formal_pushed) → 不持久化
- `action_queue` = f(suggested_next_action 的优先级链) → 不持久化
- `blocked_reason` = f(formal_synced, formal_pushed, entries_changed) → 不持久化
- governance/quality 输出 = f(HistoryManager suggest_* entries) → 不持久化
- governance/patterns 输出 = f(HistoryManager formalize entries) → 不持久化
- governance/graph 输出 = f(HistoryManager formalize/triage_accept/push entries) → 不持久化

新增 semantic 字段遵循同一条规则：**不能引入新的持久化位置**。它的值必须完全从已有的 operational + governance 层数据计算得出。

### 4. Observer Constraint

当前没有 observer 链。step_*() 是硬编码的调用序列——`step_scan()` 末尾直接调 `_run_integrity_checks()`，`step_sync()` 末尾直接调 `snapshot_tool_memories()` → `ContractManager.update()` → `harvest_lessons()`。没有 `emit(Event)` → observer 自动响应的 pub-sub 机制。

这个约束的含义：**在显式解决 observer 循环检测之前，不引入 event-driven dispatch**。硬编码的调用序列是当前天然的循环安全阀。

## D2: Discipline Validation Lint

`backend/core/state_reader.py` 新增 `_validate_discipline()` 函数。约 30 行。

调用时机：`gitgo status --json --layered` 时自动执行一次。输出 warning（不 block 执行）。

三条检查：

```python
def _validate_discipline() -> list[str]:
    warnings = []
    
    # Rule 1: governance event 类型名在 canonical 集合内
    canonical = {"governance_synced", "governance_pushed", "governance_dissolved",
                 "governance_edited", "governance_renumbered", "governance_drift",
                 "governance_contract_updated", "governance_lesson",
                 "governance_memory_snapshot"}
    entries = HistoryManager.load()
    for e in entries:
        if e.operation.startswith("governance_") and e.operation not in canonical:
            warnings.append(f"Unknown governance event: {e.operation}")
    
    # Rule 2: StateReader 的所有 public 方法不调 HistoryManager.save()
    # (静态检查——当前所有 StateReader 方法只调 load() 或 ContractManager.load())
    # 这条检查由 code review 保证——StateReader 方法如果调了 save() 会在 review 时被标记
    
    # Rule 3: semantic 层字段值与 operational/governance 层一致
    # (运行时检查——比较 status_dict(layered=True) 的 semantic 层推导值
    #  与从 governance 层独立计算的值是否一致)
    
    return warnings
```

Rule 3 的实现：

```python
# 独立从 governance 层重新计算 semantic 字段
# 与 status_dict 输出的 semantic 块做交叉验证
governance = layered["layers"]["governance"]
semantic = layered["layers"].get("semantic", {})

# entries_changed 在 operational 层
operational = layered["layers"]["operational"]
entries_changed = operational["entries_changed"]

# 独立计算
expected = "idle"
if governance["trial_pending"] > 0:
    expected = "triage"
elif entries_changed > 0 and governance["formal_synced"] <= governance["formal_pushed"]:
    expected = "formalize"
elif governance["formal_synced"] > governance["formal_pushed"]:
    expected = "push"

if semantic.get("suggested_next_action") != expected:
    warnings.append(f"Semantic inconsistency: suggested_next_action={semantic.get('suggested_next_action')}, expected={expected}")
```
