# Gitgo v0.27 — Runtime Constitution + Architecture Formalization

> 2026-05-29 | 基于 Dogfooding 完整架构理解 | 不扩功能，显式化已有结构

---

## 定位

v0.25 做了 State Convergence（C1-C3）。v0.26 做了 Runtime Discipline（4 条硬约束）。
v0.27 做的是**把已经存在的 Runtime 结构显式化**——给已有的代码正确的名字、正确的边界、正确的约束。

不改任何 step_*() 的行为。不改任何 CLI/MCP 接口。只做三件事：
1. 升级 RuntimeDiscipline 为完整 Constitution（补 4 条缺失规则）
2. 显式化三层状态机（代码注释 + 文档）
3. 命名修正（release ≠ 备份区）

## R1: Runtime Constitution 补完

`docs/RuntimeDiscipline.md` → 升级为 `docs/RuntimeConstitution.md`。

新增 4 条规则：

### 5. Layer Mutation Rules

```
mutability:
  operational layer:  mutable, transient, session-scoped
  governance layer:   append-only, cross-session
  semantic layer:     pure derivation, never persisted

具体规则:
  - operational 层的任何字段可以随 step_*() 执行而改变
  - governance 层的任何字段只能通过 HistoryManager 追加
  - semantic 层的任何字段不能写入 session.json 或任何持久化文件
  - 违反: 如果在 session.json 中发现 semantic 字段，这是 bug
```

### 6. Gate Extension Policy

```
Gate A (Semantic Legitimacy) 可扩展规则:
  - 扩展方式: 新增 Policy 模块（放入 backend/core/policy/）
  - Policy 必须实现 Policy.check(context) -> PolicyResult 接口
  - Policy 由 Runtime Kernel 在 transition 前调用
  - 不允许: Policy 直接调用 step_*() 或修改 formal_commits

Gate B (Publication Legitimacy) 可扩展规则:
  - 扩展方式: 同上
  - 不允许: Policy 在 Gate B 阶段修改代码内容（只能检查/清洗）
```

### 7. Semantic Reversibility

```
semantic 层的字段不具备可逆性:
  - suggested_next_action 是瞬时推导，不保证跨 session 一致
  - workspace_entropy 随 entries 变化，历史值不保留
  - 如果需要历史 semantic 状态，从 governance event log 重新推导

canonical state 具备可逆性:
  - 进入 Canonical Release Space 的 formal commit 不可删除（只能 dissolve 回 workspace）
  - dissolve 本身产生 governance_dissolved event，不消除历史
```

### 8. Event Taxonomy

```
所有 event 必须归类为以下 6 种之一:
  operational:  scan, formalize, sync, push, triage_*, delete_formal, dissolve_formal
  governance:   governance_synced, governance_pushed, governance_dissolved,
                governance_edited, governance_renumbered
  integrity:    integrity_warning
  publication:  governance_drift, governance_contract_updated
  knowledge:    governance_lesson, governance_memory_snapshot
  discipline:   discipline_violation (新增，_validate_discipline 触发)

新增 event 必须:
  1. 在本文档的 taxonomy 中声明类型
  2. detail 字段包含状态变更内容（governance）或操作范围（operational）
  3. 不能同时属于两个类型
```

## R2: 三层状态机显式化

### 2a: Operational State Machine（已有，加文档）

`sync_session.py` 顶部新增 module docstring 声明：

```python
"""
Operational State Machine (Layer 1)
====================================
这是 gitgo 唯一显式编码的状态机。18 个 step_*() 方法驱动状态转移。

状态转移图:
  IDLE → SCANNING → SELECTING → COMMITTING → SYNCING → PUSHING → IDLE
                ↘ TRIAL_CHECKING → TRIAL_REVIEWING → INCOMING_CONFIRMING

所有状态转移必须通过 step_*() 方法，禁止直接修改 self.stage。
"""
```

### 2b: Semantic State Machine（新增文档）

`docs/RuntimeConstitution.md` 中声明：

```
Semantic State Machine (Layer 2)
=================================
这个状态机不在代码中显式存在——它由 Gate A / Gate B 的检查逻辑隐式定义。

状态: Workspace State → Validated State → Canonical State

Gate A (Workspace → Validated):
  触发: step_sync() 中 sync_to_backup() 调用前
  检查: Policy Engine 全部 policy
  通过: governance_synced event 写入
  不通过: governance_drift / integrity_warning 写入，状态停留在 Workspace

Gate B (Validated → Canonical):
  触发: step_push() 中 push_to_backup() 调用前
  检查: authorship / privacy / security
  通过: governance_pushed event 写入
  不通过: 状态停留在 Validated
```

### 2c: Governance State Machine（新增文档）

```
Governance State Machine (Layer 3)
===================================
这个状态机分布在多个 subsystem 中，各自维护自己的隐式状态。

Formal Commit Lifecycle:
  created → synced → pushed
         ↘ dissolved

Trial Lifecycle:
  incoming → pending → accepted / promoted / discarded

Contract Lifecycle:
  feature introduced → confirmed (N times) → (可能废弃)

这些隐式状态转移的 event 记录在 HistoryManager 中，
但代码中没有统一的 GovernanceState enum。
```
