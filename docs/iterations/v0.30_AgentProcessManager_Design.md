# Gitgo v0.30 — Agent Process Manager 设计报告

> 2026-06-17 | 基于 v0.29 源码 + 四个 Agent 系统架构对比 + OS 设计哲学

---

## 一、问题的本质

### 1.1 当前 Gitgo 的治理模型有一个盲区

v0.29 完成了 Policy Engine 可插拔 + StateLog 治理循环 + lesson trigger 匹配 + rejection-driven harvest。这套治理基础设施已经完整。但它的触发方式仍然存在一个根本性的问题：**Agent 是外部进程，Gitgo 是外部进程，两者之间不存在强制接口。**

无论用什么机制——MCP tool、daemon watchdog、GATE_STATUS 文件、policy check event——只要 Gitgo 和 Agent 跑在不同的进程里，Agent 永远可以选择不理 Gitgo。这不是 Gitgo 的设计缺陷——是两个独立进程之间的物理边界。

### 1.2 当前所有 Agent 系统都是单 While-Loop

四个代表性系统：

| 系统 | Loop 结构 | Phase 概念 | 多角色 | 等级权限 |
|------|----------|-----------|--------|---------|
| Claude Code | while-turn → LLM → parse → permission → dispatch | 无 | 无 | 权限检查在 dispatch 前，但不区分 ring 级别 |
| Reasonix | provider.Stream → collect tools → execute each → repeat | 无 | Planner/Executor 二分 | 无；planner 通过 session 分离保证 cache 稳定 |
| OpenCode | Effect functional pipeline + beforeTool/afterTool hooks | 无 | Agent 定义层可配置 permission | Permission 在 Agent 定义时嵌入，不区分 ring |
| Gitgo v0.29 | daemon event loop + Policy Engine 检查 | CognitivePhase (6 states) | 无 | Gate A/B 在 governance transition 时检查 |

共同特征：**单 Agent 单 Loop。一个 Agent 做完所有事。explore、edit、commit、push 都发生在同一个 while 循环体里。** 这不是实现问题——这是架构前提。当 explore 和 push 在同一个循环体里时，Agent 永远有机会直接操作 release 仓库。Gate A/B 的检查只能发生在 Agent "同意经过"的时候。

## 二、设计哲学：从 OS 借来的三个概念

### 2.1 进程树（Process Hierarchy）

Linux 的核心世界观——**大任务必然分裂为小任务，小任务可能失败，父任务负责 fork → wait → 聚合 → 决策。**

一个进程可以 fork 子进程。子进程继承父进程的资源限制和权限。父进程可以对子进程做 wait——阻塞直到子进程完成，拿到返回值。如果子进程跑了太久、或者父进程决定它走错方向，父进程可以 kill 它。如果父进程被终止了，init 进程（PID 1）回收孤儿进程。

翻译到 Agent 系统：
- 每个项目有一个 A 级 Agent（项目管理者）。它自己不做任何代码改动。它的唯一工作是：理解用户意图、决定需要什么角色参与、分配角色为 sub-agent、fork 它们、给每个角色不同的工具集和独立的 max_steps、等待它们的产出、聚合它们的结果、对最终展示负责。
- A 级 Agent 之下是 B 级 Agent（角色执行者）。它们被 A fork，拿到特定的工具清单和上下文，做具体的规划、设计、编码、测试。它们不直接对人负责——人对最终结果的确认通过 A 汇总呈现。
- Daemon 充当 init 进程——负责回收孤儿进程，确保没有 sub-agent 的产出被遗漏。

### 2.2 特权级别（Privilege Rings）

Linux 的 ring 0（内核态）和 ring 3（用户态）。ring 0 能访问所有资源。ring 3 只能通过 syscall 请求 ring 0 的服务。

翻译到 Agent 系统：
- ring 0（A 级 Agent + Gitgo daemon）：能写 StateLog、能调 Gate 检查、能修改 contract/lesson、能执行 push/sync/accept。
- ring 3（B 级 Agent）：只能读取治理信息（读 lesson、读 contract、读 StateLog），不能直接修改。想要 push → syscall 要经过 ring 0。
- ring 3 的 Agent 想调 push 一百次都会被 gate 拦截。它只能请求 A 级 Agent 来调。A 级 Agent 读到"请求升级"信号后，自己决定是否调。

### 2.3 文件描述符继承（Tool Set Inheritance）

Linux 的 fork 之后，子进程默认继承父进程打开的文件描述符。但父进程可以在 fork 之前关闭某些 fd——子进程就访问不到。

翻译到 Agent 系统：
- 每个 sub-agent 的工具清单不是"全部可用"——是父 agent 在 fork 时显式传入的。
- 做技术规划的 sub-agent 拿不到 `write_file` 和 `exec_shell`。
- 做单元测试的 sub-agent 拿不到 `push` 和 `sync`。
- 这不是靠 prompt 约束——是工具压根不在它的 tool registry 里。

## 三、软硬分界

OS 从来不告诉用户程序"怎么编辑文本"——它只告诉你"这个文件你能不能编辑"。从不告诉你"怎么调度进程"——它只分配 CPU 时间片。**硬约束定义边界和资源分配模式，软约束在边界内保留完全的自由。**

### 3.1 硬约束的位置（边界上，极少）

| 约束 | 实现方式 | 放在哪里 |
|------|---------|---------|
| ring 0 vs ring 3 权限 | tool_registry + gate.check() | 每次 tool dispatch 前 |
| max_steps | 超了被进程管理器 kill | AgentProcess 生命周期 |
| Gate A/B | governance transition 时强制执行 | step_sync / step_push 内部 |
| fork depth ≤ 2 | 子 Agent 的 fork 方法不存在 | AgentProcessManager 设计 |
| tool set 显式传入 | fork 时传参 | AgentProcessManager.fork() |

**约束表达能力越靠近动作，越应该倾向于硬性、参数化式的配置开关；越靠近目标推理，越应该保留为软性、LLM 自主判断的空间。**

### 3.2 软约束的位置（执行过程里，LLM 自己判断）

| 约束 | 实现方式 | 放在哪里 |
|------|---------|---------|
| sub-agent 怎么完成任务 | LLM 自己决定 | sub-agent 的推理过程中 |
| 聚合结果时怎么判断一致性 | LLM 读产出后自己判断 | A 级 Agent 的 wait 后聚合 |
| 是否采纳 lesson 的 rule | 读完 rule 后 LLM 判断是否适用 | Policy Engine 匹配后注入 |
| 代码风格 / 测试策略 | LLM 根据 task 判断 | executor 自己决定 |

## 四、核心架构：Agent Process Manager

`backend/core/loop/` — 新建包，约 400 行。Gitgo daemon 之上的一层。

### 4.1 AgentProcess

一个独立的执行单元：

```python
@dataclass
class AgentProcess:
    process_id: str          # UUID
    role: str                # "planner" | "executor" | "reviewer" | "reporter"
    ring_level: int          # 0 或 3
    tool_registry: ToolRegistry   # 这个进程能调的工具
    max_steps: int           # 超了被 kill
    session_context: list    # 独立 LLM 会话
    parent_id: str | None    # 谁 fork 的
    status: ProcessStatus    # RUNNING | WAITING | COMPLETED | KILLED | ORPHANED
```

### 4.2 AgentProcessManager

管理进程树：

```python
class AgentProcessManager:
    def fork(self, parent: AgentProcess | None, role: str, 
             tool_registry: ToolRegistry, max_steps: int, 
             ring_level: int, context: dict) -> AgentProcess:
        """创建子进程。parent=None 时创建 A 级 Agent。"""
    
    def wait(self, process: AgentProcess, timeout: float | None = None) -> ProcessResult:
        """阻塞直到子进程完成或超时。"""
    
    def kill(self, process: AgentProcess) -> None:
        """终止子进程，回收它的资源。"""
    
    def reap(self, process: AgentProcess) -> ProcessResult | None:
        """回收孤儿进程——如果父进程被终止了，子进程的产出不能丢。"""
    
    def list_children(self, process: AgentProcess) -> list[AgentProcess]:
        """列出某个进程的所有子进程。"""
```

### 4.3 AgentOrchestrator（A 级 Agent 核心）

```python
class AgentOrchestrator:
    """
    项目管理者 — ring 0。不执行具体任务。
    职责：理解用户意图 → 读治理信息 → fork 角色 → wait 产出 → 聚合 → 仲裁 → 呈现。
    """
    
    def run(self, task: str, project_config: ProjectConfig) -> OrchestratorResult:
        """
        1. 读 contract + lesson（理解当前项目的约束和已知教训）
        2. LLM 推理：决定需要什么角色参与
        3. fork 各角色 sub-agent（B 级），每个有独立的工具集和 max_steps
        4. wait 所有产出
        5. LLM 聚合：判断各产出是否一致
        6. 如不一致 → fork 仲裁 sub-agent
        7. 呈现最终结果
        """
```

### 4.4 Ring Gate

每次 tool dispatch 前在进程边界上执行：

```python
class RingGate:
    RING_0_TOOLS = {"sync", "push", "accept_trial", "promote_lesson", "modify_contract"}
    
    def check(self, process: AgentProcess, tool_name: str) -> GateResult:
        if process.ring_level == 0:
            return GateResult(allowed=True)
        
        if tool_name not in process.tool_registry:
            return GateResult(
                allowed=False,
                error="TOOL_NOT_IN_REGISTRY",
                message=f"Tool '{tool_name}' is not in your tool set."
            )
        
        if tool_name in self.RING_0_TOOLS:
            return GateResult(
                allowed=False,
                error="RING_0_REQUIRED",
                message=f"'{tool_name}' requires ring 0. Request escalation to {process.parent_id}."
            )
        
        return GateResult(allowed=True)
```

## 六、与现有代码的关系

`backend/core/loop/` 是 daemon **之上**的一层。**不替代任何现有模块**：

```
daemon：感知外部事件（watchdog、stdin command reader、trial poller）
  └─ loop/AgentProcessManager：管理进程树（fork / wait / kill / reap）
      └─ loop/AgentOrchestrator：A 级 Agent 逻辑（fork 谁、怎么聚合、怎么仲裁）
          └─ loop/AgentProcess：B 级 Agent 执行单元（LLM 推理 + tool dispatch）
              ├─ policy/PolicyEngine：每次 tool dispatch 前的检查（已有）
              ├─ history/HistoryManager：StateLog 写入（已有）
              └─ steps/：纯函数步骤（已有）
```

现有的 `policy/`、`steps/`、`history/`、`state_reader.py`、`daemon/` 全部原样保留。Loop 是新的最上层。

## 七、关键设计约束

### 7.1 fork depth ≤ 2

子 Agent 不能再 fork 孙子 Agent。进程树的深度是 2——A 级 Agent（ring 0）开启 B 级 Agent（ring 3）。B 级 Agent 不能 fork。

为什么：防止权限递归。如果 B 级 Agent 可以 fork，那 C 级 Agent 的权限是继承 B 还是 A 还是自己定义的？递归权限管理是 OS 里最复杂的几个问题之一——Linux 用 user namespace 花了十年才解决。Gitgo 不应该碰这个问题。

### 7.2 每个 Agent 独立 LLM 会话

A 级 Agent 和 B 级 Agent 的 LLM 会话不共享 context。这是从 Reasonix 借鉴的最重要设计——不同角色有不同的工具集和不同的治理信息需求。Planner 需要 contract + lesson 注入到 context。Executor 只需要 plan 文本 + Policy Engine 的检查结果。共享 context 会导致 token 污染——Planner 的讨论内容进入了 Executor 的推理空间。

### 7.3 去抖窗口是多 Agent 并行的天然同步点

多个 B 级 Agent 并行工作时，Gitgo 已有的 watchdog 去抖（2 秒无 workspace_dirty 才触发 Policy Engine 检查）自动聚合它们的变更，在同步点生成统一的治理信号。不需要额外的锁或调度逻辑。

## 九、架构定位

Gitgo 的治理基础设施（StateLog、Policy Engine、Gate、Lesson、Contract）在 v0.25-v0.29 已经完整。缺失的不是"更强的治理检查"——是**一个能让治理系统在 Agent 执行流程中自然发挥作用的调度层**。

v0.30 不做 Agent——不做 LLM 推理、不做代码生成、不做 prompt 工程。v0.30 做的是 **Agent Process Manager**：一个在 Gitgo daemon 之上管理多角色 Agent 生命周期、权限、资源配额、产出回收的调度层。它补的是当前所有 Agent 系统（包括 Gitgo 自己）都缺失的那一层：**确定性约束在系统边界上，创造性自由在边界内。**
