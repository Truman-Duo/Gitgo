## 背景

当前项目处于"命令式 GUI"阶段（widget.clicked → widget.setText），但已开始出现信号追踪困难、跨 Mixin 隐式耦合的早期症状。

## 已完成的低风险铺垫（本次）

- **Semantic Token 层**：`themes/__init__.py` `SemanticTokens` 类，semantic.surface/text/border/status/commit/node 命名空间
- **信号映射表**：`panel.py` 注释块，列出全部 20+ 个 signal→slot 连接

## 暂缓事项及理由

### 1. 完整 state→render pipeline

**目标**：`WorkshopState` dataclass → dispatcher → partial rerender

**暂缓理由**：PySide6 无虚拟 DOM diff，需手写渲染 diff 层。6000 行项目阶段，投入产出比不值得。

**重估条件**：项目超过 12000 行，或出现以下症状之一：
- 同一个状态变更需要手动更新 3+ 个 widget
- 出现 repaint 循环（A 刷新 → B 刷新 → A 刷新）
- widget 之间出现 5+ 层级的相互调用

### 2. Controller/Store 架构

**目标**：Mixin → View Logic only，状态统一归 WorkshopController

**暂缓理由**：当前 Mixin 职责已接近 View Logic。真正的跨 Mixin 污染只有 `merge_btn.setEnabled()` 一处，用信号解决即可，不需要 Controller 层。

**重估条件**：Mixin 数量超过 12 个，或 3+ 个 Mixin 开始互相写对方的 `self.xxx` 字段

### 3. 完整 app/ state/ controllers/ views/ 目录重构

**目标**：state/ controllers/ views/ widgets/ theme/ services/ 六层架构

**暂缓理由**：当前 workspace/ 子包的 Mixin 拆分粒度（每个 100-300 行）刚好合适。过度拆分反而让一个 feature 需要改更多文件。

**重估条件**：workspace/ 子包超过 15 文件，或 frontend/ 总文件超过 30

### 4. Action Dispatcher 统一事件系统

**目标**：`dispatch(Action.SelectCommit(id))` 替代 `widget.clicked.connect(...)`

**暂缓理由**：Qt Signal 本身就是 dispatcher 机制。问题不是 Signal 不好，而是连接点散落。信号映射表（本次已完成）已经解决了可追踪性问题。

**重估条件**：Signal 连接超过 50 个，或出现信号循环触发

### 5. Component Tree + props 模式

**目标**：`WorkspaceCommitCard(data=commit, selected=True, on_toggle=...)`

**暂缓理由**：Qt 的 widget 树已经是 component tree，不需要再套一层 props diff。当前 `WorkspaceCommitBox(idx, type, summary, meta, parent)` 已经是 props 模式。

---

### 已知脚手架：`_build_right_panel()` 方法

**位置**：`builder.py` `BuilderMixin._build_right_panel(with_diff=True)`

**问题**：此方法是"哪里需要往哪塞"的临时方案。右侧 Diff+Node 面板作为参数传给 builder，违背"组件自治"原则。每个 Tab 应该通过自己的 View 组件声明是否需要右侧面板，而非调用 builder 的工具方法。

**何时移除**：状态驱动重构完成后，Diff/Node 变为 `state.diff_target` + `state.node_status` 的渲染结果，各 Tab 的 View 组件独立消费这两个 state 字段并渲染各自区域。届时 `_build_right_panel()` 消失，Tab 构建逻辑回归各 View Mixin 自身。
