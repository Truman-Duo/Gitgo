# v0.30 延后设计记录

> 这些设计方向是正确的，但在当前阶段（v0.30 C1-C4）做会过度工程化。
> 记录在此，供 v0.31+ 参考。

---

## D1: FileHashCache — 文件扫描 SHA256 缓存

**设计**：`backend/core/cache/file_hash.py`
- mtime+size 快速变化检测，匹配则跳过 SHA256
- 持久化到 `.gitgo/cache/file_hashes.json`
- 内存 LRU 热缓存（最近 500 个文件）
- watcher 检测到变化时主动 `invalidate(rel_path)`

**延后原因**：当前 Lexi 项目 ~200 文件，SHA256 全量扫描 <2 秒。缓存带来的加速在百文件级项目上不可感知。等 C5 验证期积累真实数据后，如果有万文件级项目再实现。

---

## D2: 合约钩子接入 ToolDispatcher

**设计**：ToolDispatcher 构造时接受可选的 ContractManager，在 `gitgo_formalize` / `gitgo_sync` / `gitgo_push` 调用前执行合约漂移检查。

**延后原因**：当前 Gate A（sync 时合约检查）和 PolicyEngine（daemon 周期检查）已经覆盖了合约执行。在 ToolDispatcher 层再加一道检查会形成三层重复（PolicyEngine → Gate A → Dispatcher），需要先简化现有两层再引入第三层。属于 v0.31 的"治理层去重"任务。

---

## D3: 每次工具调用的独立审计日志文件

**设计**：`HistoryManager.add_tool_call()` 写入 `.gitgo/tool_calls.jsonl`（追加写，与工作流历史分离）。

**延后原因**：当前 HistoryManager.add_operation() 已经支持任意 operation 字符串，`"tool_executed"` event 可以直接写入现有历史文件。独立 JSONL 文件在工具调用量 <100/天 时没有性能差异。等 C5 验证期确认工具调用频率后再决定是否需要独立存储。

---

## D4: AgentOrchestrator — 多 Agent 编排循环

**设计**：类似计划 C2/C3 描述——A 级 Agent 在 Phase 边界注入治理简报，fork B 级 Agent 执行具体任务，收集结果，聚合上报。

**延后原因**：这是 v0.30 的最终目标形态，但需要 C1（ToolDispatcher）+ C2（Context Builder）+ C4（LLM Provider）全部完成并稳定后才能实现。当前阶段应先把三个基础件做好。

---

## D5: 异步 / Streaming LLM 调用

**设计**：用 `httpx.AsyncClient` + asyncio 替代同步 `requests.post()`，支持 streaming response（SSE）。

**延后原因**：daemon 是同步架构（单线程主循环 + 后台线程）。引入 asyncio 需要改造整个事件循环。v0.30 用线程包装同步 HTTP 调用即可满足验证需求。Streaming 在治理场景下价值有限（A 级 Agent 需要完整 response 才能决策）。

---

## D6: Rate Limiting — 工具调用频率限制

**设计**：ToolDispatcher 中加 token bucket 限流，按 process_id + tool_name 维度控制频率。

**延后原因**：当前没有真实 Agent 调用，无法确定合理的限流参数。等 C5 验证期积累调用模式数据后再设计。
