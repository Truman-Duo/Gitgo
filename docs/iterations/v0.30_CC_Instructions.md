# Gitgo v0.30 基础设施实施指令

> 给 CC 的分阶段执行指令。基于 v0.29 源码 + 四个参考项目调研 + Reasonix 缓存架构分析。

---

## 总览

v0.30 的目标不是建完整的多 Agent 系统——是让 v0.29 的治理循环从"事后审计"升级为"过程控制"，同时为后续的多 Agent 架构做好基础设施：

| 阶段 | 名称 | 核心产出 | 预估 |
|------|------|---------|------|
| C1 | ToolDispatcher + RingGate 接入 | 每次 tool call 前 RingGate 检查 + tool_executed event | 1 天 |
| C2 | Context Builder | Phase 边界注入治理简报到 A 级 Agent context | 0.5 天 |
| C3 | Session 缓存策略 | A/B 级 Agent 强制分离 context + 治理数据在 session 启动时一次性读入 | 0.5 天 |
| C4 | 接入真实 API | daemon → ToolDispatcher → LLM 完整链路跑通 | 1 天 |
| C5 | Lexi 数据积累 | 在 Lexi 项目上跑 2-3 周，积累真实 governance signal | 观察期 |

**总计约 400 行新代码。不改动任何现有 step_*()、PolicyEngine、HistoryManager、Gate A/B 逻辑。**

## C1: ToolDispatcher + RingGate 接入（~150 行）

### 问题

当前 `loop/gate.py` 的 `RingGate.check()` 和 `loop/manager.py` 的 `AgentProcessManager` 都是数据结构定义——没有任何实际的 tool dispatch 路径调用它们。MCP 工具的 45 个 tool 直连 FastMCP，完全绕过 `loop/` 层。

### 目标

在 tool dispatch 之前插入 RingGate 检查 + 在 tool 执行之后记录审计 event。不改 MCP tool 的注册方式。

### 文件

新建 `backend/core/dispatch/dispatcher.py`（~130 行），新建 `backend/core/dispatch/__init__.py`（~10 行）。

### 实现

```python
# backend/core/dispatch/dispatcher.py

from dataclasses import dataclass, field
import time
from typing import Callable
from backend.core.loop.gate import RingGate
from backend.core.loop.models import AgentProcess, ProcessStatus


@dataclass
class ToolResult:
    allowed: bool
    data: dict | None = None
    error: str = ""
    duration_ms: float = 0.0
    steps_remaining: int = 0


class ToolDispatcher:
    """每次 tool dispatch 前执行 RingGate 检查，后记录审计 event。
    
    不替代 MCP tool 注册——在 MCP tool 的实际执行函数之前调用。
    """
    
    def __init__(self, gate: RingGate, tool_registry: dict,
                 history_writer: Callable | None = None):
        self._gate = gate
        self._tools = tool_registry  # {tool_name: callable}
        self._history = history_writer
    
    def dispatch(self, process: AgentProcess, tool_name: str,
                 args: dict) -> ToolResult:
        """执行一个 tool call。在每行 sink 之前跑 gate check。"""
        start = time.time()
        
        # Step 1: process status check
        if process.status != ProcessStatus.RUNNING:
            return ToolResult(
                allowed=False,
                error="PROCESS_NOT_RUNNING",
                data={"message": f"Process is {process.status.value}"},
            )
        
        # Step 2: RingGate check
        gate_result = self._gate.check(process, tool_name)
        if not gate_result.allowed:
            self._log_tool_call(process, tool_name, args,
                               allowed=False, error=gate_result.error,
                               duration_ms=0)
            return ToolResult(
                allowed=False,
                error=gate_result.error,
                data={"message": gate_result.message, 
                      "allowed_tools": process.tool_registry.list_all() if process.tool_registry else []},
            )
        
        # Step 3: Execute tool
        try:
            tool_fn = self._tools.get(tool_name)
            if tool_fn is None:
                return ToolResult(
                    allowed=False,
                    error="TOOL_NOT_FOUND",
                    data={"message": f"Tool '{tool_name}' not found in registry"},
                )
            result_data = tool_fn(args)
            duration = (time.time() - start) * 1000
            process.steps_used = getattr(process, 'steps_used', 0) + 1
            
            self._log_tool_call(process, tool_name, args,
                               allowed=True, duration_ms=duration)
            
            # Step 4: max_steps check
            steps_remaining = process.max_steps - process.steps_used
            if steps_remaining <= 0:
                process.status = ProcessStatus.KILLED
            
            return ToolResult(
                allowed=True,
                data=result_data,
                duration_ms=duration,
                steps_remaining=steps_remaining,
            )
        except Exception as e:
            duration = (time.time() - start) * 1000
            self._log_tool_call(process, tool_name, args,
                               allowed=True, error=str(e),
                               duration_ms=duration)
            return ToolResult(
                allowed=True,
                error=str(e),
                data={"message": f"Tool error: {str(e)}", "is_error": True},
                duration_ms=duration,
            )
    
    def _log_tool_call(self, process, tool_name, args, *,
                       allowed=True, error="", duration_ms=0.0):
        """写入 HistoryManager tool_executed event。"""
        if self._history is None:
            return
        self._history(
            "system", "tool_executed", "success" if allowed else "denied",
            {
                "tool_name": tool_name,
                "args_summary": str(args)[:200],
                "duration_ms": duration_ms,
                "process_id": process.process_id,
                "role": process.role,
                "ring_level": process.ring_level.value,
                "allowed": allowed,
                "error": error,
            },
            correlation_id=process.process_id,
        )
```

### 集成到 daemon

`backend/core/daemon/__init__.py` 的 `_handle_command()` 函数。新增 `{"cmd": "dispatch_tool", ...}` 处理分支。这个分支调 `ToolDispatcher.dispatch()` 替代原 MCP 直连路径。约 20 行。

### C1 认证

- [ ] ring 3 进程尝试 ring 0 工具 → 返回 RING_0_REQUIRED error
- [ ] 工具不在进程 registry → 返回 TOOL_NOT_IN_REGISTRY error
- [ ] max_steps 耗尽 → process.status = KILLED，下一步 dispatch 返回 PROCESS_NOT_RUNNING
- [ ] HistoryManager 有 tool_executed event，包含 tool_name + duration_ms + process_id
- [ ] allow 和 deny 两种情况都有 event 记录

## C2: Context Builder（~80 行）

### 问题

当前 A 级 Agent 在做调度决策时看不到治理状态——它不知道本轮变更命中了哪些 lesson、是否有 contract drift、上一轮的 rejection 原因是什么。这些信息分散在 HistoryManager、contract、lesson 的 JSONL 文件里，A 级 Agent 的 context 里只有 task + plan。

### 目标

在 Phase 边界（Planner 完成 → Executor 完成 → Reviewer 完成 → 聚合），从四个数据源各取一块信息，拼成一个 800-1500 token 的治理简报，注入 A 级 Agent context。

### 文件

新建 `backend/core/loop/context_builder.py`（~80 行）。

### 实现

四个纯函数，不调 LLM，只做数据读取 + 拼接：

```python
# backend/core/loop/context_builder.py

def build_governance_brief(
    project_name: str,
    workspace_path: str | Path,
    changed_files: list[str] = None,
) -> dict:
    """在 Phase 边界构建治理简报。
    
    返回值是一个 flat dict，每个 value 是 LLM 可读的浓缩文本。
    总计 800-1500 token。
    """
    return {
        "phase_brief": _phase_brief(changed_files or []),
        "contract_summary": _contract_summary(project_name, workspace_path, changed_files),
        "lesson_matches": _lesson_matches(project_name, workspace_path, changed_files),
        "rejection_history": _rejection_history(project_name),
        "drift_alerts": _drift_alerts(project_name),
    }
```

四个内部函数分别负责一块：

```
_phase_brief: 从 HistoryManager 读本 cycle 内所有 B 级 Agent 产出摘要（tool_executed event）
              → "Planner 方案: ... Executor A 改了 3 个文件 Executor B 改了 2 个文件"
              → 约 300-500 token

_contract_summary: 从 contract.yaml 读 decided_features，只保留本次变更文件相关的条目
              → "已确认特性: dashboard (confirmed×3) / trial (confirmed×1)"
              → 约 200 token

_lesson_matches: 从 policy_check_result event 读 matched_lessons，只取最近一次 check
              → "匹配到的 lesson: [stdin_stdout_race] 不要用 Rich Live + Windows msvcrt"
              → 约 200 token

_rejection_history: 从 rejection event 读最近 3 条的 reason + instruction
              → "第 1 次被拒原因: 颜色不对 第 2 次: 布局偏离..."
              → 约 100-200 token

_drift_alerts: 从 governance_drift event 读最近 2 条
              → "tech_stack 漂移: rich → ink"
              → 约 100 token
```

### 触发时机

不自动触发。由 A 级 Agent（ring 0）在 `fork` 之前和 `wait` 之后显式调 `build_governance_brief()`。不是 daemon 管理的——A 级 Agent 自己在 orchestration 逻辑中决定什么时候需要哪一块信息。

### C2 认证

- [ ] `build_governance_brief()` 返回合法 dict，四个 key 都存在
- [ ] 无 lesson 匹配时 `lesson_matches` 为空字符串而非异常
- [ ] 无 rejection 记录时 `rejection_history` 为空字符串
- [ ] 总 token 不超过 2000
- [ ] 所有读取是纯函数，不调外部 API

## C3: Session 缓存策略（~30 行）

### 问题

从 Reasonix 的调查结论：缓存命中率高的核心原因是 session 分离 + prepend-only context + cache-stable prefix 设计。Gitgo 的 A/B 级 Agent 已经有不共享 context 的结构，但约束没有显式化：contract 可能在 session 中间被 Policy Engine 更新，lesson 可能被收割。

### 目标

锁定三个硬约束：
1. A 级 Agent 和 B 级 Agent 的 session_context 强制分离（已有，只需文档化 + AgentProcessManager.fork 时检查）
2. contract + lesson 在 A 级 Agent session 启动时一次性读完，session 中间不更新
3. B 级 Agent 的 context 只包含 A 级 Agent 传递的 plan 文本 + C2 的 governance brief（不含 contract 原文、lesson 原文）

### 实现

`AgentProcessManager.fork()` 加约 10 行约束检查：

```python
# 在 fork() 内部的：如果 fork 的是 B 级 Agent（ring 3），检查 context 不包含 contract 原文
if ring_level == RingLevel.RING_3 and isinstance(context, dict):
    if "contract_yaml" in context or "lessons_full" in context:
        raise ValueError("B-level agent context must not contain raw contract or full lessons.")
```

`AgentOrchestrator.run()` 的初始步骤里，把 C2 的 `build_governance_brief()` 结果注入 A 级 Agent context。约 10 行。

### C3 认证

- [ ] 两个 A 级 Agent fork 的两个 B 级 Agent 的 context 不交叉
- [ ] A 级 Agent context 中的 contract lesson summary 在 session 中始终是启动时读的那份
- [ ] B 级 Agent context 不包含 contract.yaml 原始文本

## C4: 接入真实 API（~100 行）

### 问题

当前不存在任何实际的 LLM 调用。`AgentProcessManager.fork()` 只是创建了一行记录。

### 目标

在 daemon 里加一个 `llm_call` 命令分支。A 级 Agent 通过这个分支调外部 LLM API。约 80 行——用 `httpx` 或 `requests` 包装 OpenAI-compatible `/chat/completions` endpoint。不做 stream 模式，第一版只做 `chat(messages) -> text`。

### 文件

新建 `backend/core/loop/llm.py`（~80 行）。

### 实现

```python
# backend/core/loop/llm.py

class LLMProvider:
    """OpenAI-compatible /chat/completions wrapper.
    
    不绑定特定模型——model_id + base_url + api_key 全部由 config 注入。
    """
    def __init__(self, base_url: str, api_key: str, model_id: str):
        self._base = base_url
        self._key = api_key
        self._model = model_id
    
    def chat(self, messages: list[dict], max_tokens: int = 4096) -> str:
        """同步 chat completion。返回 response content 文本。"""
        import requests
        resp = requests.post(
            f"{self._base}/chat/completions",
            headers={"Authorization": f"Bearer {self._key}"},
            json={
                "model": self._model,
                "messages": messages,
                "max_tokens": max_tokens,
            },
            timeout=120,
        )
        data = resp.json()
        return data["choices"][0]["message"]["content"]
```

### 接入 daemon

daemon `_handle_command()` 新增 `{"cmd": "llm_call", "messages": [...], "process_id": "..."}`。调 AgentProcessManager 找到对应 process → 更新它的状态 → 返回 LLM 响应。

### C4 认证

- [ ] 发一条空消息 → 返回 LLM response 文本
- [ ] process.status 保持 RUNNING
- [ ] LLM response 写入 HistoryManager 的 `llm_response` event
