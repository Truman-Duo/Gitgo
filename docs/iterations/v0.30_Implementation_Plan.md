# Gitgo v0.30 — StateLog 2.0 + AgentProcessManager 最小版

> 2026-06-17 | 综合 Code Research + OS Design + 两轮反馈

---

## 版本定位

v0.25-v0.27：状态收敛与约束固化（Governance Runtime 基础设施）
v0.28-v0.29：Dashboard / Policy Engine / Steps / StateLog 治理循环（Governance Runtime 运行态）
v0.30：StateLog 升级 + Agent 执行环境基础（Governance Runtime → Agent Runtime Kernel）

v0.30 的重点不是建一个完整的 Agent Framework——是完成两件事：
1. 把 StateLog 从 append-only event log 升级为 Event → Fact 两层分离的治理知识系统
2. 建立一个最小可运行的 Agent Process Manager，作为多 Agent 环境下 Fact 数据的生产源

两者同时做，因为 Fact Engine 的设计需要多 Agent 数据来验证。先让最少的东西跑起来，积累真实 pattern 后再扩展。

## 二、L0: HistoryEntry 升级

### 目标

当前 `HistoryEntry` 字段都是"发生了什么"——operation、status、detail。缺少"这些事件之间的关系"——哪个 event 触发了哪个 fact、哪个 event 是哪个 event 的后续、这次修正因为哪个之前的错误而产生。

### 新增字段

```python
@dataclass
class HistoryEntry:
    timestamp: str
    project_name: str
    operation: str
    status: str = "success"
    detail: dict = field(default_factory=dict)
    correlation_id: str = ""
    
    # ── L0 新增 ──
    fact_refs: list[str] = field(default_factory=list)
    # ["fact_file_modified_frequently_dashboard_py", "fact_rejection_chain_round5"]
    # 本 event 触发了哪些 fact 的派生
    
    tags: list[str] = field(default_factory=list)
    # ["exploration", "abandoned", "rejected"]
    # 标记此 event 的语义类别
    
    parent_event_id: str = ""
    # 本 event 的前驱 event 的 correlation_id
    # 例：rejection 的 parent 是被拒绝的 formalize
    # 用于构建 event 因果关系
    
    # 保留旧字段向后兼容
    file_count: int = 0
    commit_hash: str = ""
    commit_message: str = ""
    workspace: str = ""
    backup: str = ""
```

三个新字段全部有默认值，完全向后兼容。

### 改动范围

`history.py` — `HistoryEntry` dataclass 新增 3 字段。`add_operation` / `add_suggestion` / `add_entry` 签名不变。现有 9 种写入点不需要改——新的 `fact_refs`/`tags`/`parent_event_id` 在写入时默认空。Fact Engine 在追加 event 时设置这些字段——写入方法和 Now 完全一致。

## 三、L1: Fact Engine

### 目标

不是建一个"Event → Fact → Rule → Decision"四层全架构。是建一个**最小的 Fact derivation 层**——从 HistoryManager 读取原始 event，计算出高频 pattern 的 fact，写回 HistoryManager。

### 文件：`backend/core/fact/`

```
backend/core/fact/
├── __init__.py          # derive_facts() 统一入口
├── file_patterns.py      # 文件级别的 fact（高频修改、共变、删除恢复）
├── workflow_patterns.py  # 工作流级别的 fact（burst、rejection chain、exploration）
└── contract_patterns.py  # 合约级别的 fact（drift、架构违反、依赖断裂）
```

约 150 行。每个 pattern 文件是独立的 `derive_*_facts()` 函数，纯数据读取 + 计算，零副作用。

### Fact 的类型

```python
@dataclass
class Fact:
    fact_id: str           # "fact_file_modified_frequently_dashboard_py"
    fact_type: str         # "file_frequently_modified" | "rejection_chain" | "exploration_abandoned" | "contract_drift_repeated"
    summary: str           # "dashboard.py 在最近 10 次 scan 中被修改了 7 次"
    related_events: list[str]  # ["scan@2024-...", "formalize@2024-..."]
    derived_at: str        # ISO timestamp
    project_name: str
    severity: str          # "low" | "medium" | "high"
```

### derive_facts() 统一入口

```python
def derive_facts(project_name: str) -> list[Fact]:
    """从 HistoryManager 读取最新 event，计算新的 fact。去重，返回新增的 fact 列表。"""
    entries = HistoryManager.load()
    recent = [e for e in entries if e.project_name == project_name][-50:]
    
    facts = []
    facts.extend(derive_file_facts(recent))
    facts.extend(derive_workflow_facts(recent))
    facts.extend(derive_contract_facts(recent))
    
    # 去重
    existing_ids = {e.detail.get("fact_id", "") for e in entries 
                     if e.operation == "fact_derived"}
    new_facts = [f for f in facts if f.fact_id not in existing_ids]
    
    # 写回 HistoryManager
    for f in new_facts:
        HistoryManager.add_operation(
            project_name, "fact_derived", "success",
            {"fact_id": f.fact_id, "fact_type": f.fact_type, 
             "summary": f.summary, "related_events": f.related_events, 
             "severity": f.severity},
        )
        # 反写 fact_refs 到源 event
        for e in recent:
            if e.timestamp in f.related_events or e.operation in ["scan","formalize","rejection"]:
                if f.fact_id not in e.fact_refs:
                    e.fact_refs.append(f.fact_id)
    
    return new_facts
```

### 触发时机

Daemon 的 `workspace_dirty` 去抖之后，Policy Engine 检查之前，调 `derive_facts()`。约 5 行改动。

## 四、L2: Lesson / Governance 迁移读 Fact

### 目标

现有的 harvest.py 和 governance/* 模块从原始 event 直接推导结论（"同一个文件改了 3 次"）。改为优先从已有的 fact_derived event 读取——如果某种 fact 已经存在，直接消费它，不做重复计算。

### 改动范围

`harvest.py` 的 `_harvest_from_governance_signals` — 在扫描 governance event 之前，先查是否有对应 fact_derived event。如果有 `fact_rejection_chain_round5` → 直接用它生成 lesson，不需要再手动分析 rejection event。

`governance/quality.py` 的 `compute_quality_metrics` — 优先从 fact_derived event 读取"已采纳/已修改/已拒绝"的计数。

约 40 行改动。不影响现有的"从 raw event 推导"的 fallback 逻辑。

## 五、L3-L5: AgentProcessManager 最小版

### 设计原则

- **只有 process 生命周期管理，没有 agent 思维**
- **只有 ring 权限检查，没有 prompt 模板**
- **只有 tool registry 传递，没有任务分解逻辑**

### L3: AgentProcess 数据模型（`loop/models.py`，~60 行）

```python
from dataclasses import dataclass, field
from enum import Enum

class ProcessStatus(Enum):
    RUNNING = "running"
    WAITING = "waiting"
    COMPLETED = "completed"
    KILLED = "killed"
    ORPHANED = "orphaned"

class RingLevel(Enum):
    RING_0 = 0  # 治理权限：能调 sync/push/accept/promote_lesson
    RING_3 = 3  # 执行权限：只能调本进程 tool_registry 里的工具

@dataclass
class AgentProcess:
    process_id: str          # UUID
    role: str                # "planner" | "executor" | "reviewer" | "reporter"
    ring_level: RingLevel
    tool_registry: "ToolRegistry"
    max_steps: int
    status: ProcessStatus
    parent_id: str | None    # 谁 fork 的
    result: dict | None = None  # wait 之后的产出
    created_at: str = ""
```

### L3: ToolRegistry（`loop/tools.py`，~40 行）

```python
class ToolRegistry:
    """Per-process tool set。fork 时由父 Agent 显式传入。"""
    
    RING_0_TOOLS = {"sync", "push", "accept_trial", "promote_lesson", "modify_contract"}
    
    def __init__(self, tool_names: list[str]):
        self._tools = set(tool_names)
    
    def has(self, tool_name: str) -> bool:
        return tool_name in self._tools
    
    def is_ring_0(self, tool_name: str) -> bool:
        return tool_name in self.RING_0_TOOLS
    
    def list_all(self) -> list[str]:
        return sorted(self._tools)
```

### L4: AgentProcessManager（`loop/manager.py`，~120 行）

```python
class AgentProcessManager:
    """进程树管理器。daemon 之上的调度层。"""
    
    def __init__(self):
        self._processes: dict[str, AgentProcess] = {}
    
    def fork(self, parent_id: str | None, role: str, 
             tool_registry: ToolRegistry, max_steps: int, 
             ring_level: RingLevel) -> AgentProcess:
        """创建子进程。parent_id=None 时为 A 级 Agent (ring 0)。"""
        # fork depth ≤ 2 检查：
        # 如果已有 A 级 Agent (parent_id=None) 且当前 parent_id 非空，
        # 检查 parent 自己是不是已经被 A 级 Agent fork 的
        if parent_id is not None:
            parent = self._processes.get(parent_id)
            if parent and parent.parent_id is not None:
                raise ValueError("Fork depth exceeds 2. B-level agents cannot fork.")
        
        process = AgentProcess(
            process_id=str(uuid.uuid4()),
            role=role,
            ring_level=ring_level,
            tool_registry=tool_registry,
            max_steps=max_steps,
            status=ProcessStatus.RUNNING,
            parent_id=parent_id,
            created_at=datetime.now().isoformat(),
        )
        self._processes[process.process_id] = process
        
        # 写入 StateLog
        HistoryManager.add_operation(
            "system", "agent_forked", "success",
            {"process_id": process.process_id, "role": role, 
             "ring_level": ring_level.value, "parent_id": parent_id},
            correlation_id=process.process_id,
        )
        return process
    
    def wait(self, process_id: str, timeout: float | None = None) -> dict | None:
        """阻塞直到子进程完成。超时返回 None 不 kill。"""
        process = self._processes.get(process_id)
        if not process:
            return None
        
        start = time.time()
        while process.status == ProcessStatus.RUNNING:
            if timeout and time.time() - start > timeout:
                return None
            time.sleep(0.5)
        
        return process.result
    
    def kill(self, process_id: str) -> None:
        """终止子进程。标记为 KILLED，它的产出被保留在 process.result。"""
        process = self._processes.get(process_id)
        if process and process.status == ProcessStatus.RUNNING:
            process.status = ProcessStatus.KILLED
            HistoryManager.add_operation(
                "system", "agent_killed", "success",
                {"process_id": process_id, "role": process.role},
            )
    
    def reap(self) -> list[AgentProcess]:
        """回收孤儿进程——父进程已死但本身还在的进程。"""
        active_ids = {p.process_id for p in self._processes.values() 
                      if p.status == ProcessStatus.RUNNING}
        orphans = []
        for p in self._processes.values():
            if p.parent_id and p.parent_id not in active_ids:
                p.status = ProcessStatus.ORPHANED
                orphans.append(p)
                HistoryManager.add_operation(
                    "system", "agent_reaped", "success",
                    {"process_id": p.process_id, "role": p.role,
                     "parent_id": p.parent_id},
                )
        return orphans
```

### L5: RingGate（`loop/gate.py`，~80 行）

```python
class RingGate:
    """每次 tool dispatch 前在进程边界上执行的权限检查。"""
    
    def check(self, process: AgentProcess, tool_name: str) -> GateResult:
        if process.ring_level == RingLevel.RING_0:
            return GateResult(allowed=True, reason="ring_0_bypass")
        
        if tool_name not in process.tool_registry.list_all():
            return GateResult(
                allowed=False,
                error="TOOL_NOT_IN_REGISTRY",
                message=f"Tool '{tool_name}' is not in your registry. Your tools: {process.tool_registry.list_all()}",
            )
        
        if ToolRegistry.RING_0_TOOLS and tool_name in ToolRegistry.RING_0_TOOLS:
            return GateResult(
                allowed=False,
                error="RING_0_REQUIRED",
                message=f"'{tool_name}' requires ring 0. Request escalation to parent {process.parent_id}.",
            )
        
        return GateResult(allowed=True, reason="ring_3_allowed")
```

## 六、L6: 观察期（2-3 周）

### 目标

不是加功能。是让 L3-L5 的最小 ProcessManager 在 Lexi 项目上挂载真实 Agent，积累多 Agent 环境下的治理数据。

### 运行环境

```
项目：Lexi（已有 gitgo_config）
Agent 模型：通过 llm.py 的 provider 抽象层接入（Anthropic / OpenAI）
角色配置（直接在 loop 初始化代码里写，不用 contract.yaml）：
  - planner: ring 3, max_steps=15, tools=[read_file, search_code, glob, read_lesson, read_contract]
  - executor: ring 3, max_steps=50, tools=[read_file, write_file, exec_shell, search_code, glob]
  - reviewer: ring 3, max_steps=20, tools=[read_file, search_code, glob, read_lesson]
```

### 观察指标

| 指标 | 数据源 | 期望 |
|------|--------|------|
| 多 Agent event 类型分布 | HistoryManager operation 统计 | 新的 event 类型出现（agent_forked、agent_killed、agent_reaped、ring_0_escalation） |
| fact_derived event 数量 | fact_derived event count | 非零，且每周有新 fact |
| fact 类型分布 | fact_type 统计 | 出现单 Agent 环境下不存在的 fact type |
| lesson harvest 精度 | pending.jsonl 数量 + 人工 review 准确率 | rejection_chain / exploration_abandoned 类 fact 被正确转化为 lesson |
| fact_refs 回溯可用性 | 从 fact_derived event → related_events → 原始 event 的查询耗时 | 查询在 500ms 内完成 |
| Policy Engine trigger 匹配率 | policy_check_result 里的 matched_lessons 数量 | 非零（lesson trigger 匹配到了当前文件） |
| Rejection chain 触发率 | rejection event count → rejection_count≥3 → lesson harvest | 产生真实的 rejection-driven lesson |
| Drift 检测假阳性 | governance_drift 数量 vs 人工 review | 假阳性率低（预估阈值需调的 drift 模式） |
| Ring Escalation 频率 | ring_0_escalation 或 ring gate 拒绝次数 | 出现 ring 3 Agent 尝试 ring 0 工具被拒绝的真实场景 |

### 观察方式

每周从 HistoryManager dump 一次分析报告。不需要新代码——用现有 `governance quality --json` 和 `history --json` 查询。如果某些 fact 模式在 2 周内完全没出现，说明单 Agent 环境无法产生这种 pattern——验证了反馈中"多 Agent 数据是 Fact Layer 的前提"的判断。

## 九、核心原则

1. **Fact Engine 是基于已有数据的最小抽象，不是四层架构的预先设计。** L1 只做三种最确定的 fact pattern（文件级、工作流级、合约级），其他类型等 L6 数据。
2. **AgentProcessManager 是生命周期管理，不是 Agent 思维。** fork/wait/kill/reap——这些是 OS 的原语。A 级 Agent 怎么分配任务、怎么聚合产出——这些是 LLM 的推理，不写在 ProcessManager 里。
3. **fork depth ≤ 2。** A 级 Agent 可以 fork B 级 Agent。B 级 Agent 不能 fork。违反是硬错误。这是从 Linux user namespace 学来的——递归权限是这个 OS 模式下唯一必须硬性阻止的东西。
4. **L6 不是停滞，是数据积累。** 当前整个 Agent 行业没有人知道"多 Agent 环境下的治理事实长什么样"。在 Lexi 项目上积累 2-3 周的观察数据，比继续往设计文档里加架构图更有价值。
