# Gitgo Loop 设计调研报告

> 2026-06-17 | 四个 Agent 系统 Loop 架构对比

---

## 概览

四个系统覆盖了 AI coding agent loop 的全部设计空间：

| 系统 | 语言 | 架构类型 | Loop 核心 | Key 独特贡献 |
|------|------|---------|-----------|-------------|
| Claude Code | TypeScript | Monolithic harness | while-turn → LLM → parse → permission → dispatch | ToolCallConnected/Disconnected 双模、permission 在 dispatch 前、compaction 时保留 brief + digest 前缀 |
| Reasonix | Go | Config-driven thin harness | provider.Stream → collect tool calls → execute each → repeat | Session 分离保证 prefix cache 稳定、Provider/Tool registry 接口化、Coordinator 两模型分工 |
| MiMo/OpenCode | TypeScript | Plugin-driven harness | Effect.effect 纯函数式、Permission 在 agent 定义阶段嵌入、Skill/Plugin 两扩展层 | Permission 作为 agent 定义的一部分（非运行时触发）、Pipeline hook (beforeTool/afterTool)、原生并行 tool dispatch |

---

## 1. Claude Code — Monolithic While-Loop

**源码**：`dist-nosplit/cli.js`（80 万行打包文件）

### Loop 结构

从源码提取的关键信号：

```
while (task_not_done):
    assemble context (prompt + files + history)
    → LLM call (stream response)
    → parse tool calls from response
    → for each tool call:
        permission check
        → if allow: execute tool (connected 或 disconnected 模式)
        → if deny: reject with explanation
    → append tool results to context
    → if context > limit: compaction
    → evaluate stop conditions
```

### Tool Dispatch

两种模式通过 `handleToolCall` 分发：
- `handleToolCallConnected` — socket bridge 正常时走 MCP 调用
- `handleToolCallDisconnected` — 断开时返回错误消息

### Permission

三个层级：
1. `permissionMode` (ask / skip_all_permission_checks / follow_a_plan)
2. `permissionOverrides` 对单次 tool call 覆盖
3. `DENY` 硬阻断 + 解释

### Compaction

token >0.8 context window 时触发。保留 user turns + prior digest。在任意位置进行摘要，边界对齐并移除孤立的 tool 结果。

特点：compaction 结果修改历史以控制 token，这是重量级操作——每次触发暂停进度若干秒。

### 对 Gitgo Loop 的启发

- **负向学习**：Claude Code 没有显式 phase 概念——explore/edit/commit 在 harness 眼里是同一个 while 循环体。这不仅会导致 scope creep，还容易在长时间运行时出现"能力递减"现象——在同一个 while 循环体中反复处理，失去目标，上下文逐渐累积并污染后续推理
- **正向学习**：tool dispatch 双模（connected/disconnected）简洁有效；compaction 时保留 brief + digest 作为固定的 cache-stable 前缀很重要
- Gitgo Loop 应该有不同的 phase（planner→executor→reviewer），在每多轮自主 loop 结束时强制进入 Phase 过渡。以约束抑制过量低质量 token 对后续自主推理的污染，并通过强制过渡刷新目标共识，避免 agent 在局部循环中越陷越深

## 2. Reasonix — Config-Driven Thin Harness

**源码**：Go 单二进制，`internal/agent/` 为核心

### Loop 结构（SPEC.md §3.4）

```go
func (a *Agent) Run(ctx context.Context, input string) error {
    for step := 0; step < a.maxSteps; step++ {
        req := buildRequest(a.session.Messages, a.toolRegistry)
        chunks := a.provider.Stream(ctx, req)
        // print text deltas live, collect completed tool calls
        if len(toolCalls) == 0 { break }
        for _, tc := range toolCalls {
            result := a.executeTool(ctx, tc)
            a.session.Append(result)
        }
    }
}
```

### 独特贡献

**Coordinator（两模型分工）：**
- Planner 模型：read-only 工具集，生成 concise plan，运行在独立 session 中
- Executor 模型：全工具集，接收 planner 的 plan 文本 → 执行
- 两个 session 永不混合 → 各自的 prefix cache 稳定，token 成本低

**Config-driven 无硬编码：**
- Provider 是 interface（`Stream(ctx, req) → chan Chunk`），OpenAI-compatible 是唯一实现
- Tool 是 interface（`Execute(ctx, args) → result`），内置工具 + 外部 MCP 插件通过 registry 注入
- 切换到不同的 LLM provider 只需一次 TOML 配置更改，不需要修改 loop 代码

三、**显式 loop bound**——通过 max_steps 在运行时限制总的循环迭代次数（planner 和 executor 独立设置各自的 max_steps）。不仅可以防止 LLM 陷入无限循环，还具有**经济适配性**——对于不同预算水平的用户，可以通过调整 max_steps 控制单次任务成本上限，而无需修改任何系统配置

### Permission

permission 是 per-call 策略：allow / ask / deny → Decision。在 tool execute 之前做判断，不在 agent 定义层。

### 对 Gitgo Loop 的启发

- **最重要**：Coordinator 的 Planner/Executor session 分离可以直接借鉴——Gitgo 的 governance 需要 planner（理解 task + 查 contract + 查 lesson）和 executor（写代码）在独立的 context 空间运行。Planner 的 session 可以注入 contract + lesson，Executor 的 session 不需要——它只需要 plan 文本 + Policy Engine 的检查结果。Planner 和 Executor 是 Gitgo Loop 的两个自然 phase。
- Provider/Tool 的 interface 化表明 Gitgo Loop 不需要绑定特定 LLM——抽象 `llm.Stream(prompt) -> chunks` 接口，具体实现（anthropic / openai / ollama）由 config 注入
- Config-driven 模式意味着 Gitgo Loop 的 phase 配置应该来自 `contract.yaml`——不是代码 if/switch，是配置决定启用哪些 phase

## 3. OpenCode / MiMo-Code — Plugin-Driven Harness

**源码**：`packages/opencode/src/agent/agent.ts`

### Agent 定义层

Agent 不是运行时动态配置的——Agent 定义时就包含了 permission ruleset、model ID、tool set、prompt：

```typescript
{
  build: {
    name: "build",
    mode: "primary",
    permission: Permission.fromConfig({ question: "allow", plan_enter: "allow", ... }),
    model: { modelID: "...", providerID: "..." },
    prompt: PROMPT_BUILD,
  },
}
```

Permission 是 agent 定义的组成部分（通过 `Permission.merge` 多层合并），不是运行时独立配置的。

### Plugin / Pipeline

OpenCode 的 plugin 系统允许 hook 到 agent 生命周期——`beforeTool` / `afterTool` 拦截点。每个 tool call 在 dispatch 之前经过 plugin pipeline 处理（validation / transformation / blocking）。

### 与 Reasonix / Claude Code 的对比

| 维度 | Claude Code | Reasonix | OpenCode |
|------|-----------|---------|---------|
| Loop 类型 | Monolithic while | Interface-based while | Effect-based functional |
| Permission 位置 | 每次 dispatch 时 | per-call 独立检查 | 在 agent 定义层嵌入 |
| 扩展方式 | MCP 工具 | Plugin + Builtin registry | Plugin + Skill + PluginBoot |
| 并行工具 | 推断为串行 | registry 可配置并行 | 原生并行 batch dispatch |

### 对 Gitgo Loop 的启发

- Agent 定义模型意味着 Gitgo Loop 应该支持多个 "agent 角色"——不是在运行时动态创建，而是在启动时由 `contract.yaml` 定义：planner agent（读 contract/lesson）、executor agent（写代码）、reviewer agent（在执行后检查结果是否符合治理规则）
- OpenCode 的 permission-in-definition 模式与 Gitgo 的 Gate 概念互补——Permission 回答"这个 agent 能不能执行这个 tool"，Gate 回答"当前治理状态允许这个操作吗"
- Pipeline hook 是 Phase Gate 嵌入 Agent harness 的理想拦截点——但 OpenCode 的实现方式（Effect functional）与 Gitgo 的 Python 生态不兼容，不应直接模仿实现模式

## 4. MiMo-Code — OpenCode 改版

**源码**：与 OpenCode 同构（共享 `@opencode-ai/core` + 自定义 TUI）

MiMo 在 OpenCode 基础上的独特贡献：
- Permission 集成到 agent 定义——`mimocode.jsonc` 中声明
- TUI 是自定义 React 终端（`@anthropic/ink`），与 Gitgo Dashboard 同技术栈
- 无独立的 governance 层——没有 contract、lesson、drift detection

## 5. 四个系统对 Gitgo Loop 的汇总启示

### 架构启示

| 来源 | 启示 | Gitgo 对应物 |
|------|------|-------------|
| Claude Code | while-turn loop 简洁但缺 phase → scope creep + 能力递减 → 必须引入 phase gate | Gitgo 的 CognitivePhase 枚举 + Gate A/B |
| Reasonix | Session 分离保持 cache 稳定 | Planner/Executor 分离 session |
| Reasonix | Provider/Tool interface 化 + config-driven | `llm.Stream()` 抽象 + contract.yaml 注入 |
| Reasonix | 显式 loop bound（max_steps）防无限循环 + 成本控制 | Planner 和 Executor 各自独立 max_steps |
| OpenCode | Agent 定义层嵌入 permission | Gate 在 agent 定义阶段配置 |
| OpenCode | Plugin pipeline (beforeTool/afterTool) | Policy Engine check 在 tool dispatch 前 |
| Claude Code | Compaction 保留 brief + digest 前缀 | Gitgo 的 StateLog brief 作为不可压缩前缀 |

### 最关键的设计决策

1. **多 Agent 角色而非单 while-loop**：Reasonix 的 Planner/Executor 分离是最重要的启示——不同角色有不同的 tool set、不同的 context、不同的 session。Gitgo 的 governance 需要至少三个角色：Planner（理解 task + 查 contract/lesson）、Executor（写代码）、Reviewer（执行后验证治理规则）。每个角色的 session 独立，不共享 context，各自保持 cache 稳定

2. **Phase 不是代码 if/switch——是配置**：Reasonix 的 config-driven 设计表明 agent 的 phase 链应该从 contract.yaml 定义。用户不需要修改 loop 代码来加一个 phase——只需要在配置中声明 phase 的定义和衔接模式

3. **Permission + Gate 是两个不同层，需要在不同位置表达**：OpenCode 的 permission-in-definition 是"agent 能不能执行 tool"的静态约束。Gitgo 的 Gate 是"当前治理状态是否允许这个操作"的动态约束。两者不应混淆——Permission 在 tool 定义层表达，Gate 在每个 tool dispatch 前动态检查

4. **去抖是多 agent 并行时的天然同步点**：Gitgo 已有的 watchdog 去抖机制（2 秒无 workspace_dirty 才触发 Policy Engine 检查）恰好构成多 agent 并行时的天然同步点——多个 executor 同时工作时，去抖窗口自动聚合它们的文件变更，在检查时生成统一的治理反馈

5. **Loop Bound = 成本控制**：不仅是为了防止无限循环——max_steps 本质上是一种预算约束。免费模型可能无所谓，但调用商业 LLM 时，每一步都是成本。给 Planner 和 Executor 各自设定独立的 max_steps，可以让用户根据预算和需求自由调整——Planner 阶段尽量快速生成 plan（低 max_steps），Executor 阶段可以给更多探索空间（高 max_steps），而且每个项目的配置可以不同
