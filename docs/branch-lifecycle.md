# 分支与接纳生命周期

欢迎主动贡献，无需先被 assigned。作者可以在自己的 fork 调查、修复、实验并提交 PR；assigned 用于协调责任，不是开工或提交许可。维护者负责提供公开入口、审查与接纳，贡献者不需要主仓库写权限。

`master` 是经批准和组合验证的版本基线。普通维护 PR 先进入固定维护分支，大型或高风险任务进入约定的专属接纳分支；维护者再整合版本。贡献接纳、基线更新和打包发布是三个独立步骤，不能相互代替授权。

## 如何选择 PR 目标

| 情况 | 默认目标 / 处理方式 |
|---|---|
| 范围清楚、兼容性影响有限的 bug、文档或测试改进 | [`maint/alpha3.1`](https://github.com/Truman-Duo/Gitgo/tree/maint/alpha3.1)，可直接从 fork 开 PR，不等维护者逐项创建目标 |
| 新模块、跨组件重构、权限/隔离/持久恢复等高风险修改 | 尽早讨论方向、接口、依赖和验收，维护者协调专属目标；合入前核对目标与范围 |
| 已明确目标的任务、后续阶段或堆叠 PR | 使用约定的目标和依赖；目标调整须沟通并重新验证，不自动改投维护分支 |
| 版本整合 | 维护者另行批准的整合分支向 `master` 提交基线 PR |

分流依据是影响、依赖和风险，不是行数或作者身份；小补丁也可能改变安全边界。疑似安全漏洞按 [安全报告](../SECURITY.md) 处理。目标不确定时可以先提 Issue、公开 fork 中的实验，或在现有入口开明确标记“方案讨论、待确定接纳目标”的 Draft PR；维护者应帮助确定合适目标，不要求先获得 assigned。Draft 不保证方案被接受，也不免除合入前的范围、权限和验证要求。

当前固定维护入口从 Alpha3.1.1 的 `15e5a82a5510adaa658535d87f5b657e5c21e545` 建立，包含该版 Windows 沙箱 P0 修复。维护分支会继续前进；作者以 fetch 后的实际目标为基线，不固定使用这个初始 SHA，也不把 Alpha3.2 在途开发混入稳定版修复。未来开发入口由维护者明确公布，不能猜测尚不存在的分支。

现有 Rust、工作台和已经约定目标的修复继续使用各自接纳分支；本流程不自动迁移既有 PR 或丢弃其依赖。准备大规模投入前讨论可减少返工，但不禁止作者自主实验或提出不同方案。

## 分支角色

| 角色 | 用途 | 保留到何时 |
|---|---|---|
| 开发源分支 | 提交一个任务的实现和修正，可位于 fork | PR 合并且确认没有新增成果或依赖后清理 |
| `maint/<series>` 固定维护分支 | 公开接收该版本系列的普通维护 PR，累积已审查成果 | 该系列仍接收贡献时持续保留；结束维护前公布替代入口并处理未完成依赖 |
| 专属接纳分支 | 接收大型、高风险或需独立验证任务的 PR | 版本整合完成、内容可追溯且无活动依赖后清理 |
| 版本整合分支 | 组合多个已接纳功能，处理冲突并验证 | 更新基线并保存版本引用后清理 |
| `master` | 经批准和验证的当前版本基线 | 长期保留，不删除或重写 |
| `release/<version>`、版本 Tag | 保存各版本的准确基线 | 长期保留，不能作为临时分支清理 |

开发源分支和接纳分支必须是两个不同的引用。例如自己的 `fix/read-error` 向 `maint/alpha3.1` 提交普通维护 PR；`feat/native-invocation-recovery` 向 `feat/sandbox-recovery-v1` 提交专属任务 PR。分支名本身不证明接纳状态，以实际 PR 和提交为准。

## 开发与对齐

1. 普通维护从公开入口的实际提交创建自己的开发分支，不要求等 assigned 或单独授权开工。检查已有 Issue/PR，说明复现、范围和预期行为；有重复工作时协调，不把协调机制变成参与许可。
2. 维护者主动分配任务时，必须同时给出可用的接纳目标、准确基线、依赖和验收要求；普通任务可复用固定维护入口。需要专属目标时由维护者从约定基线创建并回读核验，不能把它直接创建在候选 head 上冒充 PR 合并。
3. PR 正文声明准确的源和目标仓库、分支、候选 head SHA、验证 base SHA，并说明实现、验证、兼容、回滚和未完成范围。
4. 每次修订及提交审核前 fetch，核对实际目标与前置依赖。对齐的是约定版本和目标分支，不应把其他版本的在途开发混入候选。
5. 若重新指定目标，重新核对差异、祖先关系、head/base、测试组合和检查结果。旧目标上的绿灯不能自动代表新组合通过。
6. 相关 P0 或必要基线修复出现时，维护者先在相应接纳目标保留应继承的修复，再通知作者对齐。不能只要求作者更新版本而将目标留在旧基线；已有成果不得被强推覆盖。不同版本的在途功能不机械混合。

普通维护的操作示例及远端选择见 [贡献指南](../CONTRIBUTING.md#普通维护-pr-的开始方式)。已经开始的工作先保存，再合入必要的目标更新，不要求为了目标调整重做修复。

## 审查与接纳

1. 审查设计、可靠性、安全边界、格式、证据和剩余限制。CI 通过不能代替设计判断；模块尚未完成的边界要查明并写入公开限制。
2. 核对 CI gate 及相关检查属于当前候选和目标。维护与专属目标使用同一套 CI；缺少远端保护规则不等于可以跳过检查。早期 Draft 可用于获得反馈，验收未完成须明确记录。
3. 接纳时取消 Draft，确认普通维护目标是固定维护分支，专属任务目标仍是约定分支；两者都不是 `master`。发现修改超出普通维护范围时，先与作者协调拆分或调整目标，更新证据，不因未事先分配任务而关闭 PR。
4. 维护者依照 [提交格式](../CONTRIBUTING.md#commit-格式) 协调全局编号，检查所有已发布接纳分支的占用情况，保留贡献者身份。默认 squash；需要保留已规范化提交时先核对历史再选择 merge commit。
5. 合并后核验 GitHub 显示 Merged、合并提交属于目标分支、实际内容一致。记录 base、候选、合并提交、检查证据、限制以及清理责任；确认 `master` 未被本次功能接纳改变。

## 版本基线与发布

维护者从指定版本基线建立整合分支，纳入固定维护分支中已接纳的修复及所选专属成果；合并冲突和共享边界必须重新验证，不能把各 PR 单独通过当作组合通过。维护分支合入一项修复不会自动更新 `master`、改变已发布版本或触发正式发布。普通维护版本不需要等待无关的大功能完成，也不因此混入下一版开发。

更新 `master` 前保留上一版本的准确基线引用，再经单独授权的版本整合 PR 更新。基线不得 force-push。版本更新后将相同修复传播到仍受影响的开发/专属目标，核对是否已等效修复和依赖，避免后续版本重新引入旧问题。

打包、正式终端试用及发布按各自验收要求执行。若用户要求先试用，必须等用户明确满意才能发布；功能合并或基线合并都不代替试用批准。

## 清理与保留

完成接纳或版本整合后，由维护者核对本仓库范围内的分支清单：

1. 记录待删除分支的完整 SHA、接纳 PR、保留提交及保留原因；清单和本地备份放开发材料目录，不放产品 `.gitgo`。
2. 检查未合并提交、开放 PR、堆叠依赖、活动 worktree、未提交及忽略内容。存在独有成果或归属不明时保留，并记录复查条件。
3. 普通 merge 可用祖先关系检查。squash 不保留源提交祖先关系，必须另核验已接纳内容和源分支是否又有新增提交，不能单凭 `git branch --merged` 决定删除或保留。
4. 合并完成后先清理已交付的源分支。专属接纳分支在对应版本组合验收之前保留，不能与源分支一起自动删除。固定维护入口在该系列仍接收贡献时持续保留；即使暂时与 master 相同或已被 master 包含，也不能据此删除公共提交入口。
5. 活动 worktree 的分支先保留；解除绑定前另行保存未提交、忽略内容和恢复引用。分支清理不包含删除工作树、数据库、日志或构建证据。
6. 删除远端分支时核对其仍指向已审查的 SHA，发现并发更新立即停止删除；随后清理本地无依赖引用并核验远端清单。
7. 不删除他人的 fork 分支；不删除 `master`、版本基线或仍被使用的维护/专属接纳分支。版本系列结束维护时，先公布替代入口，迁移或处理开放 PR 和依赖，再按授权归档。暂停或暂留时写清责任人、原因及退出条件。

已经结束的源分支不复用承担新任务。需要继续开发时，从明确的基线或接纳分支另建开发分支，并走新的 PR。
