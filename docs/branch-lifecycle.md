# 分支与接纳生命周期

`master` 是版本基线。功能 PR 只能合入独立功能接纳分支；维护者把多个已接纳功能组合、验证后，另行批准更新 `master`。功能接纳、基线更新和打包发布是三个独立步骤，不能相互代替授权。

## 分支角色

| 角色 | 用途 | 保留到何时 |
|---|---|---|
| 开发源分支 | 提交一个任务的实现和修正，可位于 fork | PR 合并且确认没有新增成果或依赖后清理 |
| 功能接纳分支 | 接收该任务的 PR，保存已接纳成果 | 版本整合完成、内容可追溯且无活动依赖后清理 |
| 版本整合分支 | 组合多个已接纳功能，处理冲突并验证 | 更新基线并保存版本引用后清理 |
| `master` | 经批准和验证的当前版本基线 | 长期保留，不删除或重写 |
| `release/<version>`、版本 Tag | 保存各版本的准确基线 | 长期保留，不能作为临时分支清理 |

开发源分支和功能接纳分支必须是两个不同的引用。例如源分支 `feat/native-invocation-recovery` 向 `feat/sandbox-recovery-v1` 提交 PR。分支名本身不证明接纳状态，以实际 PR 和提交为准。

## 开发与对齐

1. 开始前确认版本、准确基线 SHA、接纳分支、前置依赖和维护者。缺少接纳目标时先联系维护者，不以 `master` 作为默认接纳目标。
2. 维护者从约定基线创建功能接纳分支；不能把它直接创建在候选 head 上冒充合并。开发者从约定基线和依赖开展工作。
3. PR 正文声明准确的源和目标仓库、分支、候选 head SHA、验证 base SHA，并说明实现、验证、兼容、回滚和未完成范围。
4. 每次修订及提交审核前 fetch，核对实际目标与前置依赖。对齐的是约定版本和目标分支，不应把其他版本的在途开发混入候选。
5. 若重新指定目标，重新核对差异、祖先关系、head/base、测试组合和检查结果。旧目标上的绿灯不能自动代表新组合通过。

## 审查与接纳

1. 审查设计、可靠性、安全边界、格式、证据和剩余限制。CI 通过不能代替设计判断；模块尚未完成的边界要查明并写入公开限制。
2. 核对 CI gate 及相关检查属于当前候选和目标。功能目标使用同一套 CI；缺少远端保护规则不等于可以跳过检查。
3. 功能 PR 接纳时取消 Draft，确认目标仍是独立功能分支。不得仅为获得 Merged 标记而改动 `master`。
4. 维护者依照 [提交格式](../CONTRIBUTING.md#commit-格式) 协调全局编号，检查所有已发布接纳分支的占用情况，保留贡献者身份。默认 squash；需要保留已规范化提交时先核对历史再选择 merge commit。
5. 合并后核验 GitHub 显示 Merged、合并提交属于目标分支、实际内容一致。记录 base、候选、合并提交、检查证据、限制以及清理责任；确认 `master` 未被本次功能接纳改变。

## 版本基线与发布

维护者从指定版本基线建立整合分支，合入多个已接纳功能；合并冲突和共享边界必须重新验证，不能把各功能单独通过当作组合通过。更新 `master` 前保留上一版本的准确基线引用，再经单独授权的版本整合 PR 更新。基线不得 force-push。

打包、正式终端试用及发布按各自验收要求执行。若用户要求先试用，必须等用户明确满意才能发布；功能合并或基线合并都不代替试用批准。

## 清理与保留

完成接纳或版本整合后，由维护者核对本仓库范围内的分支清单：

1. 记录待删除分支的完整 SHA、接纳 PR、保留提交及保留原因；清单和本地备份放开发材料目录，不放产品 `.gitgo`。
2. 检查未合并提交、开放 PR、堆叠依赖、活动 worktree、未提交及忽略内容。存在独有成果或归属不明时保留，并记录复查条件。
3. 普通 merge 可用祖先关系检查。squash 不保留源提交祖先关系，必须另核验已接纳内容和源分支是否又有新增提交，不能单凭 `git branch --merged` 决定删除或保留。
4. 合并完成后先清理已交付的源分支。功能接纳分支在对应版本组合验收之前保留，不能与源分支一起自动删除。
5. 活动 worktree 的分支先保留；解除绑定前另行保存未提交、忽略内容和恢复引用。分支清理不包含删除工作树、数据库、日志或构建证据。
6. 删除远端分支时核对其仍指向已审查的 SHA，发现并发更新立即停止删除；随后清理本地无依赖引用并核验远端清单。
7. 不删除他人的 fork 分支；不删除 `master`、版本基线或仍被使用的接纳分支。暂停或暂留时写清责任人、原因及退出条件。

已经结束的源分支不复用承担新任务。需要继续开发时，从明确的基线或接纳分支另建开发分支，并走新的 PR。
