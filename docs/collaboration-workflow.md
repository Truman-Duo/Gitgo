# 多人、多仓库的变更协作模型

状态：设计与贡献约定（2026-10-09）。本次没有实现新的后端/前端工作流、自动同步、分布式锁、分支保护或自动清理。当前执行规范见 [CONTRIBUTING](../CONTRIBUTING.md)。

## 三角色与实际拓扑

workspace 是可修改的工作上下文；trial 是固定候选的评估/集成上下文；formal 是特定协作范围中明确指定的正式目标。角色不等于仓库，也不等于分支数量。

一个协作网络可以包含多个作者、fork、clone、linked worktree、workspace 和 trial。一个物理仓库可承载多种角色；一个角色也可分布在多个仓库。候选归属具体目标，不以本机的 origin、分支名字或“大家最后都差不多”推定权威。

每个正式目标都需要明确：托管服务/主机、仓库稳定身份、目标完整 ref、管理权限和接纳策略。Gitgo 上游目标是 GitHub 的 Truman-Duo/Gitgo、refs/heads/master。URL 和 origin/upstream 是访问别名；本地 clone/worktree 的运行身份与远端仓库身份分别管理。Git common dir 可关联本机 linked worktree，但不能把不同作者的独立 clone/fork 当成共享一个可写工作区。

fork 的 master 默认是上游基线的下游副本，不能称作“已被上游接纳”。若下游维护自己的产品线，可有本地正式目标；一次进入下游正式线不会自动进入上游正式线，需要独立的上游候选和接纳记录。“一条主线”适用于一个明确的正式目标，并不禁止其他独立项目有自己的正式线。

个人模式可将 workspace、trial 和 formal 的物理载体合并，仅保留必要检查与结果记录，不要求创建 fork、PR、额外试用仓库或额外的重复审批。多人模式复用同一变更模型，增加真实发生的协作、权限和同步边界。

## 管理对象与三叉

以变更提案作为长期身份，以候选版本作为一次审查对象。一个提案可能跨多个作者/仓库迭代；候选至少固定源仓库、源 ref/head、目标仓库/ref、基线、范围/内容摘要和依赖版本。多个 commit 可以组成一个候选，不按临时列表 index 定义它。

| 审查结论 | 后续流转 |
| --- | --- |
| pending | 继续审查，或记录缺信息/环境/依赖等阻塞 |
| approved | 满足当前目标的检查和授权后执行接纳；批准本身不意味着已合入 |
| changes_required | 记录可操作的问题与复评条件，继续加工，不关闭提案或删除分支 |
| rejected | 记录拒绝原因，结束当前候选，按保留/清理策略收尾 |

作者撤回、需求取消、重复或被新版替代，可使用关闭原因表达，不必各新增一套审查结论。工作暂停或设施故障不是拒绝。部分接纳需要明确拆分候选和剩余工作，不能将整个提案标成成功。

promote 是把固定候选转入指定 workspace 的加工动作，必须写明来源、目标、责任人；可以由原作者返工，也可以转交维护者，不必重复造分支。Agent 的 promote_agent_changes 当前表示批准结果进入用户 workspace，不能自动等价为进入上游 master。

审查意见、实际应用结果和资源清理分开记录。已批准但执行失败保留结论和恢复原因；结果不明先核对，不能盲目重放。已合入但清理失败仍是已合入，只重试清理。正式结果撤销通过新的 revert/修复候选进行。

## 上游更新与下游策略

上游正式更新产生一个可观察的基线变动。可以自动 fetch/提示新基线；fetch 只更新远端跟踪引用，不代表可自动修改用户 checkout、fork 默认分支或活动任务。首次记录基线也不应无声忽略已有待处理贡献。

| 下游情形 | 同步策略 |
| --- | --- |
| 纯镜像、无独有提交 | 有明确同步授权后 fast-forward；发现分叉停止，不 reset/force 覆盖 |
| 有下游独有提交 | 在同步候选中集成上游，处理冲突并验证；保留下游历史与产品决定 |
| 活动共享功能分支 | 根据责任人与任务安排带入上游；默认 merge，不替其他作者 rebase |
| 作者独占功能分支 | 可以明确选择 rebase，但确认未共享；后续审查按新候选版本进行 |
| 脏工作区或活动任务占用 | 保留现场，提示或使用独立 trial；不自动 checkout、stash、reset |
| 固定 Release/Tag 消费者 | 保持固定版本，另行评估升级；不因上游更新自动跟随 master |

同步 fork 默认分支与更新其功能分支是两项动作。每个下游分别保存已观察和已采用的基线，以及冲突/阻塞，不能使用一个全局 last_known_head 代表整个网络。

候选内容更新时，新版本需要重新评估受影响的结论。目标主线更新时，旧集成证据失去对新组合的证明能力；内容审查能否保留取决于其绑定范围，不能全部无条件复用，也不必所有审查一律重做。依赖按具体候选/正式结果绑定，不能只依赖可移动的分支名称。

## 并发与一致性

1. 并行开发和验证使用独立 workspace/worktree，分别拥有 index 和工作目录。仅共享仓库对象或 common dir 不意味着可以同时修改同一 checkout。
2. 本机按实际受影响的 checkout、index、目标 ref 管理短时写入所有权；需要同时持有多项资源时按稳定顺序获取。不能用一把全局锁阻塞不同作者和无关仓库。
3. 不同机器不能依赖本地进程锁。接纳提交时重新读取目标并检查 expected-old-head，由 Git/托管平台完成有条件更新；不能凭“刚 fetch 过”覆盖并发更新。
4. 同一目标 ref 的提交点串行或使用合并队列；候选开发/测试仍可并行。两个候选在同一旧 base 各自通过，不证明依次合入后的组合通过。
5. 输入、候选、集成树、证据和决策绑定版本。冲突解析得到新内容时重新验证；批准不授予额外工具或远端权限。
6. 跨仓库操作不是一个数据库事务。分别记录尝试、远端确认和下一步；推送超时先查询目标，候选去重/幂等记录避免重复合入。不同正式目标的接纳结果互不代替。
7. 清理前再次核对分支 expected head、使用者、关联 PR/依赖和未保存内容，只删除自己拥有且已结束的资源。squash/rebase 接纳不能只靠祖先关系判断，需正式结果与候选的对应证据。
8. 审计和清理分离；异常、结果不明和通知投递失败保留可查询诊断。旧事件不能覆盖更新版本的状态。

Git ref CAS 只能保护引用更新；它不能解决 checkout 文件并发写入，也不能证明语义兼容。平台保护规则可以作为共享执行边界，但不是全网络分布式事务。最小实现应先支持明确身份、单目标接纳和失败恢复，再增加实际需要的多目标同步。

## 复用与未来实施范围

复用现有 Git/File adapters、Host 权限、ToolPipeline 回执、worktree 快照/封存、StorageRuntime/CAS、恢复与事件投影。Git/平台是提交与 PR 状态事实源，SQLite 保存提案、版本、决策和操作关联，CAS 保存不可变证据；UI 使用 Host 投影，不自行驱动另一套 Git 状态。

现有单个 ProjectConfig.trial、last_known_head、processed_incoming、SessionStage 和 FormalCommit synced/pushed 布尔值不能直接表达网络协作。需要按目标和候选建模，逐步迁移旧数据并保持旧接口兼容；历史 discarded 不能无证据推断为拒绝还是待完善，应标为旧语义，必要时重新评估。

当前 review_child_outcome 将 reject 映射为 changes_required，旧 trial promote 记为已处理且创建分支使用 FETCH_HEAD，accept 冲突会尝试 -X theirs。这些是后续流程实施要解决的边界，本次没有将设计描述为已经实现。

前端将来应显示作者/来源、明确正式目标、候选与基线版本、审查结论、阻塞、接纳确认和清理进度；多人协作必须避免所有候选共用一个全局流程状态。常态简洁显示，详细证据按需展开。
